# WebUI 设计依据（参考 riic.autos 的结果，实现自写）

> **授权说明**：本项目所有者向 riic.autos 作者取得**仿照其结果进行设计**的授权；作者**未提供源码**，所有者亦授权对前端做逆向以作参考。
> **本文档的性质**：记录我们**学到什么**（信息组织与设计体系），**不复制**其代码、CSS 变量命名之外的实现、配色数值或素材。
> 逆向仅用于学习；落到本项目的每一行 CSS/JS 都是我们自己写的。

## 1. 从参考站学到的三件事（结论）

### 1.1 设计靠「语义化 token」，不靠「一处一个颜色」

对参考站前端 CSS 的分析结果：**322 个 CSS 自定义属性**，其中关键是**语义角色**而非具体色值：

```
--background / --foreground     页面底色与正文
--card / --card-foreground      卡片与其文字
--muted / --muted-foreground    次要信息
--border / --accent             描边与强调
--chart-1 … --chart-5           数据可视化色序
```

**含义**：深色/浅色**共用同一套 token**，切换主题只换 token 值，组件样式一行不改。
**我们的现状**：CSS 里东一处西一处写颜色，加一个元素就得再挑一次色——**这是「丑」的结构性原因**，不是选色不好看。

### 1.2 信息按「用户的实体」分组，不按数据结构分组

参考站的排班相关内容按**基建布局**组织（贸易站 / 制造站 / 发电站 / 宿舍 / 控制中枢 / 会客室 / 办公室 / 加工站 各自成块），而不是把房间条目平铺成一张表。

**含义**：用户脑子里想的是「我那两间贸易站放了谁」，不是「`rooms.trading[0].operators`」。**界面的分组应当跟随用户的模型。**

### 1.3 一屏能回答「我现在该干什么」

参考站的入口页把流程压成三步（账号 → 导入 BOX → 生成排班），每一步都有「当前步骤 / 待开始」的状态。

**含义**：面向用户的面板不该是「把所有数据列出来」，而是**让用户一眼看出下一步动作**。

### 1.4 实际看到界面后的补充观察（2026-09-29，来自用户提供的截图）

在此之前只能从 CSS 反推，拿到截图后才看清它真正的做法。**与我们的差异不止配色，而是信息架构。**

**顶部是「仪表盘」，不是内容区。** 从上一个包（U5/V1.5.6）往下，顺序是：一排状态卡（各带图标与数值）→ 一条进度条（`最接近第 2 班·匹配率 45%`）→ 班次分段控件 → 操作按钮 → 才是房型内容。
**含义**：先回答「现在什么状况」，再给内容。我们当前是**一进来就把房间全倒出来**，没有铺垫。

**房型卡片是「有边界的小盒子」，不是一列行。**
- 左上角**房型色竖条**（控制中枢深蓝 / 贸易站青绿 / 制造站金黄 / 发电站绿 / 宿舍紫蓝…）——**靠颜色区分房型，不必读字**
- 标题带**人数徽标**（小圆点）
- 内容区是**方形头像网格**，头像下方是名字，**头像左下角有职业小图标**
- 存在「AUTO / 自动补位」的**虚线占位格**（宿舍 4），表示待补位而非空缺

**它的卡片里有效率数值**（如 `223.5% = 103% + 113.3% 技能效率 + 7% 跨设施`）——**这一块我们明确不学**：那是排班效率计算，属于参考站与用户自选工具的职责（用户已明确「排班由用户上那个网站解决」）。

**「太密」的结构性原因（我们）**：缺留白、缺层级、缺「先看什么」的顺序——所有信息按同一权重堆叠。**这不是配色问题，是信息架构问题。**

**据此新增的设计约束**：

8. **页面要有「顶部概览 → 主操作 → 内容」的层次**，而不是把内容平铺在最前。
9. **房型用颜色区分**（每种房型一个语义色 token），**卡片必须有明确边界**（底、圆角、描边）。
10. **干员用「头像 + 名字」的方形网格**呈现，而不是一行顿号文字；头像缺失时回退首字色块（见 §2 第 5 条）。
11. **留白是信息，不是浪费**。相邻房型卡之间、卡片内部各元素之间都要有稳定间距；宁可让用户滚动，也不要把一屏塞满。
12. **不学它的效率数值与匹配率**——那是排班计算的产物，不属于本插件的职责。

## 2. 本项目要落到的设计约束（下一版 WebUI 按此实现）

1. **颜色只能通过语义 token 使用**。禁止在组件里写死十六进制色值（唯一例外：徽章文字色等对比色，需注释说明为什么）。
2. **深浅色共用一套 token**，用 `prefers-color-scheme` 切值，组件样式不重复。
3. **房间按房型成块**，每块标题自报数量（「贸易站 ×2」）——已有实现保留并延续。
4. **状态要能一眼看懂**：已导入/未导入、模块可用/不可用、绑定/未绑定，都要有明确的视觉表达，不能只靠一行小字。
5. **零外部资源**：不引 CDN、字体、图片（离线可用；也避免版权问题）。图标用**中文房型首字**这类自洽方案。
6. **移动端优先**：QQ 机器人用户很可能用手机开面板；网格必须能折行。
7. **不给用户算我们会算错的东西**：不预估产出、不做排班优化（那是参考站的职责）。我们只呈现「排班表说了什么」+「什么时候该换」。

## 3. 与游戏机制的关系（见 05-infra-mechanics.md）

调研结论改变了这个插件的定位，界面也要跟着改：

- 心情**不是瓶颈**（恢复约为消耗的 5 倍），所以**不要**做「疲劳条」「危险预警」这类暗示「不换就减产」的表达。
- 游戏自带队列轮换与自动休整，所以**不要**做「帮你决定换谁」。
- 真正会忘的是**「想起来该换」**——界面应当突出**下一次换班的时刻与倒计时**，以及「这一班该上谁」的清单。
