# MAA 远程控制接入说明

> 面向**使用者**。讲的是「你要做什么、看到什么算成功、出错往哪查」。
> 开发侧的协议依据与设计取舍见 [`docs/project-plan/09-maa-trigger-assessment.md`](../project-plan/09-maa-trigger-assessment.md)。

---

## 1. 这是做什么的

MAA 有一个官方的**远程控制协议**：MAA 会**主动、按固定间隔**去问你指定的一个地址「有没有任务要我做」。

本插件按这个协议提供两个端点。**开启后**，你的 MAA 就能和插件握手。

**✅ 当前版本可以真的让它跑一次**——但**必须由你先确认**。开启并配好之后，你发一句 `/ak maa run`，插件才会把一条任务放进队列，MAA 下次轮询（约 1 秒）取走并开始跑。**没有你的确认，队列永远是空的**，它不会自己跑任何东西。

**⚠️ 一条比"能不能跑"更重要的事**：MAA 每跑完一次基建任务，会把它内部的**班次索引永久前进一格**（写进配置、不会自动纠正）。所以**「派一次」等于「换一次班」**——多派一次就多跳一班。插件的做法是：**同一次换班只允许一个任务**，重复确认不会产生第二个。这条约束的来龙去脉见 `docs/project-plan/10-maa-shift-switching.md` §4.3。

**方向很重要，也是常见误解**：不是插件去连你的电脑，**是你的 MAA 主动来连插件**。所以：

- ✅ 你**不需要**在电脑上开任何端口
- ✅ 你**不需要**装内网穿透（frp / Tailscale / Cloudflare Tunnel 之类）
- ✅ 你**不需要**装任何额外软件（已核实 6.18.0 的配置里就带有这个能力）

**端点的路径由插件决定，不是 MAA 规定的。** 官方文档原话是「端点路径随意」——所以你必须**照抄本插件给出的地址**（见第 6 节），自己改路径不会通。

## 2. 能做什么、不能做什么

| | 说明 |
| --- | --- |
| ✅ 让 MAA 连上插件 | 配好之后，它会每秒来问一次 |
| ✅ **按你的确认让它跑一次** | 发 `/ak maa run`；取走、跑完、汇报，全过程回一句话给你 |
| ✅ 什么也不跑 | 你不确认，队列永远是空的 |
| ✅ 在 QQ 里查统计 | 发 `/ak maa` 看连接、队列、最近回报 |
| ✅ 没跑成会告诉你 | 电脑没开（一直没人来取）、或取走了没回报，都会主动通知 |
| ✅ 选择「我自己换」 | 发 `/ak maa skip`，不派新任务。**如果那一个还没被取走**，它就真的不会跑、班次索引不动；**已经被取走的话拦不住**（只能补发一条停止指令），那种情况下索引照样前进——见第 2 节「撤销的窗口极短」 |
| ❌ **不能指定班次** | MAA 基建任务的官方措辞是「**立即根据当前配置**，单独执行一键长草中的对应子功能」，协议里**没有**任何字段能传班次、`plan_index` 或文件路径。**能"让它现在跑"，不能"让它跑第 2 班"。** 跑到哪一班由 MAA 按它自己的排班规则决定 |
| ❌ **不能拉起没开着的 MAA** | 协议的方向是 MAA 主动来问；它得**先自己在运行**。电脑上没开 MAA 时，这个插件碰不到它 |
| ✅ **到换班时刻会主动问你一次** | 见第 9 节——它只是问；你不回就什么都不发生 |
| ❌ 不能替你改 MAA 的设置 | 排班表、定时器仍然只在 MAA 客户端里配 |

### 怎么用（四个指令）

```
/ak maa          看状态：连上没有、队列里有什么、最近一次回报
/ak maa run      让它跑一次（排一个任务，等 MAA 下次来取）
/ak maa skip     这一班我自己换，不给 MAA 派任务
/ak maa cancel   撤掉待取任务；已被取走的会补发一条「尝试结束」指令
```

`run` 之后你会收到一句回执；MAA 取走并跑完、汇报回来时，你会再收到一句**如实**的转达（说「已执行」，不说「成功了」——理由见下面的陷阱）。

### ⚠️ 撤销的窗口极短，别指望它

**任务排进队列后大约一秒内就会被 MAA 取走**（它每秒轮询 `getTask`）。所以：

- **还没被取走**：`cancel` 真的能拦住——它不会被下发。
- **已经被取走**：`cancel` **拦不住它跑**。协议里唯一相关的手段是 `StopTask`，官方原文说它「将会**尝试**结束当前运行的任务」，而且「**不会等待并确认当前任务已停止才会返回**」。所以插件会补发这条指令，但**只能说"已发送"，不能说"已停止"**。
- **它已经跑完了**：什么都改不了，**班次索引已经前进了一格**。

**实用建议**：想避免误跑，**宁可先不确认，也不要事后撤销**。确认之前你有无限时间；确认之后只有大约一秒。

> 这一条是**实测出来的**：所有者那次撤销，日志显示任务 `14:06:55.665` 排队、`14:06:55.668` 就被取走——**中间只隔 3 毫秒**。「撤销」这个动作在时间上几乎不可能赢。

### ⚠️ 一条必须知道的陷阱

MAA 官方文档原文写着：

> 一般不论任务执行成功与否只会返回 SUCCESS，只有特殊情况才会返回 FAILED

也就是说 `status: SUCCESS` **不等于「换班换成功了」**，它更像是「这条指令我处理完了」。本项目在任何文案里都不会用它宣称成功——将来也不会。

## 3. 前置条件：你的 AstrBot 要能被 MAA 访问到

MAA 是在**你自己电脑上**主动出站去连插件的，所以它必须能访问到你的 AstrBot。**这件事由你自己解决，插件帮不了你**，常见做法：

| 你的情况 | 做法 |
| --- | --- |
| AstrBot 在**有公网 IP 的服务器**上 | 直接用那个 IP / 域名（最常见） |
| AstrBot 在**家里内网** | 用你自己的反向代理、或自建隧道、或端口映射——**随你**，前提是 MAA 能访问到 |
| AstrBot 就装在**同一台电脑**上 | 用 `http://127.0.0.1:<面板端口>` 即可 |

**⚠️ 建议用 HTTPS。** 官方文档明确说：若端点是 HTTP，MAA 会在**每次连接时**弹不安全警告，而且「在外网上部署明文传输服务是极不推荐且危险的行为，仅供测试使用」。

> **关于自签证书**：如果你的 AstrBot 用的是**自签证书**（浏览器会提示「不安全」那种），**MAA 会直接拒绝**——2026-09-29 已实测，报错原文是 `UntrustedRoot`。原因是 MAA 走系统信任库，**不认这张证书背后的签发者**；这与证书是谁生成的无关，任何用自签证书的人都会撞上。怎么过这一关见**第 6 节**（导入受信任的根证书颁发机构，或换一条不涉及证书的路）。

**如果你走反向代理**：请确保路径**原样透传**，不要把 `/api/v1/plugins/extensions/...` 重写掉。

## 4. 第一步：打开模块开关

在 AstrBot 面板的**插件配置**页里找到本插件，把：

```
modules.maa  →  开启
```

**它默认是关闭的**——因为它需要你在自己电脑上做配置，不该默认替你打开。

打开后，插件日志里应出现：

```
[ak_toolbox][maa] 模块已装载，等待 MAA 轮询（还没收到过请求）。换班提醒与其它模块不受本模块影响。
```

---

## 5. 第二步：创建一个 API Key

这两个端点是**受权限保护的**（需要 `plugin` 权限范围），所以 MAA 必须带一把钥匙。

在 **AstrBot 面板里创建一个 API Key**，并给它 **`plugin` 权限范围**。

> **说明**：我们核实的是**权限机制**——插件路由要求 `plugin` 范围，而面板签发的 Key 可以带范围。**面板上具体在哪一页、按钮叫什么，会随面板版本不同**，以你实际看到的界面为准。

> **⚠️ 两件事请知情**：
> 1. 这把 Key 会出现在**你的 MAA 配置里**，也会出现在**服务器/反代的访问日志里**（因为它走在 URL 的查询串上）。
> 2. **只为这个用途建一把**，需要时可以随时撤销重发。

**为什么 Key 必须走查询串？** 因为 MAA 的远程控制设置**只能填一个普通 URL**，加不了自定义请求头——而查询串是 URL 里唯一能携带凭据的位置。所以两个地址长这样：

```
...?api_key=<你的 Key>
```

---

## 6. 第三步：在 MAA 里填两个地址

在 MAA 的**远程控制**设置里，填下面两个地址（把 `<...>` 换成你自己的）：

```
<你的AstrBot地址>/api/v1/plugins/extensions/astrbot_plugin_arknights_toolbox/maa/getTask?api_key=<你的KEY>

<你的AstrBot地址>/api/v1/plugins/extensions/astrbot_plugin_arknights_toolbox/maa/reportStatus?api_key=<你的KEY>
```

`<你的AstrBot地址>` 就是你打开面板用的地址，例如 `https://your-domain.example` 或 `http://192.0.2.10:6185`——**结尾不要带 `/`**。

### 路径写成这样是有原因的（照抄即可）

- **插件名只出现一次。** 多写一遍（`.../extensions/<插件名>/<插件名>/maa/getTask`）**匹配不上**，服务器只会回一句「未找到该路由」。
- **方法必须是 POST**，两个端点都是。
- **大小写敏感**：`getTask` / `reportStatus` 的 `T`、`S` 是大写。

> 这三条不是从文档抄的，是在真实 AstrBot 上用它的**路由匹配函数**跑出来的：单插件名 = 命中，写重 = 不命中，方法不对 = 不命中。

另外 MAA 那侧通常还有一个**设备标识 / 用户标识**要填，随便起一个你能认出来的名字即可（插件侧只记它的**长度**，不记内容）。

**如果你的 MAA 版本带「测试连接」按钮，请用它。** 官方文档的范例工作流里就有这个用法——连接不通时它会当场给出失败提示，比等轮询日志快得多。

### ⚠️ 必读：自签证书会让 MAA 直接拒绝（2026-09-29 实测）

**如果你的 AstrBot 用的是自签证书**（自己签的、没买 CA 证书），MAA 会在「测试连接」时当场报错：

```
连接测试失败，原因：The remote certificate is invalid because of
errors in the certificate chain: UntrustedRoot.
```

**这不是网络不通、不是地址写错、不是 API Key 有问题**——是 MAA（.NET 写的）**不认这张证书背后的签发者**。这是它的默认安全策略，**与本插件无关**，任何使用自签证书的人都会撞上。两条出路：

1. **把服务器这张证书装进你这台电脑的「受信任的根证书颁发机构」**（推荐，一次性，之后长期可用）。
   先在服务器上导出证书（`fullchain.pem`），核对它的 SHA256 指纹，然后**用管理员身份**跑：
   ```
   certutil -addstore -f Root <证书文件的完整路径>
   ```
   或在文件管理器里**双击证书** → 安装证书 → 选**「本地计算机」** → 「将所有证书放入下列存储」→ 浏览到**「受信任的根证书颁发机构」**。
   **装完必须完全退出 MAA 再打开**（它启动时才读证书存储），然后重新点「测试连接」。
   > **⚠️ 安全边界**：导入根证书意味着这台电脑会信任这张证书签发的任何东西。它安全的前提是**私钥只在你自己服务器上**。所以**只导你自己服务器的证书**，并且导之前核对指纹。
2. **换一条不涉及证书的路**（例如自己开一条到 AstrBot 的隧道，让 MAA 连 `http://127.0.0.1:...`）。代价是那条路得你自己维护。

> 这一条**不是**从我们的部署里推出来的通用结论——**你的证书、你的信任库，都得你自己决定**。我们只如实记录：**自签证书会让 MAA 拒绝，报错原文就是 `UntrustedRoot`**。

## 7. 怎么确认接通了

填完并保存后，MAA 会按固定间隔（默认 **1 秒**）开始轮询。**几秒内**应能观察到：

**看日志**（最直接）：

```
[ak_toolbox][maa] ✅ 首次收到 MAA 请求，连接是通的（公网可达 + 证书被接受 + 轮询已开始）。
```

**或在 QQ 里发**：

```
/ak maa
```

会回一份统计，例如：

```
【MAA】已收到 42 次请求，最近一次 09-29 15:04:11
领任务 21 次 / 汇报 21 次
最近请求体形状：{user=<str, len=6>, device=<str, len=8>}
```

**⚠️ 统计存在内存里，插件一重启就清零。** 这是刻意的：这个功能的用途正是「**刚刚那次重启之后，MAA 到底连上没有**」——清零反而让这件事看得更清楚。

### 日志不会每秒刷一条（这是有意设计的）

MAA **每秒**来一次，如果每一次都写一行日志，一天就是 86400 行——**真正要紧的事**（首次连上、任务被取走、回报到达、任务超时作废）会全部被埋在里面。

所以插件的日志是这么分的：

| 什么时候 | 级别 | 内容 |
| --- | --- | --- |
| **第一次收到请求** | INFO | `✅ 首次收到 MAA 请求，连接是通的……` |
| **每隔约一小时** | INFO | `持续连接中：过去约 60 分钟收到 3600 次请求……` |
| **其余每一次轮询** | DEBUG | 请求的路径、来源、User-Agent、请求体形状 |
| **派任务 / 任务被取走 / 回报到达 / 超时 / 报错** | INFO 或更高 | **一条都不会被省略** |

**所以「它还在连吗」有两个答案**，都不需要翻 DEBUG 日志：

- **看 `/ak maa`** —— 次数与最近一次时间，最直接；
- **看日志里的小时摘要** —— 说明它过去一小时一直在来。

**需要逐次细节时**（排查地址写错、UA 不对之类），把日志级别调到 `DEBUG`，每一行请求的形状都还在——**降级不等于删除**。

## 8. 排障

按顺序走，每一步都能自己定位：

### ① `/ak maa` 显示「还没收到过请求」

请求没到，或者到了但**没被路由到插件**。可能的原因（按常见度）：

| 原因 | 怎么确认 |
| --- | --- |
| **证书不被 MAA 接受**（自签证书） | 看 MAA 那侧有没有报错/警告；这是已知的第一风险 |
| **地址写错**（最隐蔽的一种） | 用下面 ④ 的 curl 自测 |
| Key 不对 / 权限范围不对 | curl 会返回 **401** |
| 电脑没开、或 MAA 没在运行 | 那就根本不会有请求——这不算故障 |
| 网络不通（DNS / 防火墙 / 反代） | 从 MAA 那台机器上 ping / curl 你的地址 |

> **⚠️ 地址写错时最难查**：请求**确实到达了你的服务器**（所以访问日志里有记录），但因为路径没匹配上，**插件的统计不会增加**——从插件这侧看，它和「根本没连上」长得一模一样。
> **区分办法**：去看**服务器 / 反向代理的访问日志**。里面有 `.../maa/getTask` 的记录 = 请求到了、路径可能不对；完全没有 = 请求根本没发出（网络或证书问题）。

### ② curl 返回 401

Key 或权限范围不对。检查：

- 建 Key 时**有没有给 `plugin` 权限范围**；
- URL 里的 `?api_key=` 后面那一串**有没有被空格或换行污染**；
- Key 是否已被撤销。

### ③ curl 返回 HTTP 200，但内容是「未找到该路由」

**Key 是对的，路径是错的。** 照第 6 节的地址逐字核对——最常见的就是**插件名写了两遍**。

### ④ 直接用 curl 试

在**能访问到 AstrBot 的那台机器**上执行（把变量换成你自己的）：

```bash
curl -sS -X POST \
  "https://your-domain.example/api/v1/plugins/extensions/astrbot_plugin_arknights_toolbox/maa/getTask?api_key=YOUR_KEY"
```

- 期望：`{"tasks": []}`
- 拿到 `{"status":"error","message":"未找到该路由",...}` → **路径写错了**
- 拿到 401 → **Key / 权限范围问题**
- 连不上 / 证书报错 → **网络或证书问题**（curl 加 `-k` 可临时跳过证书校验，仅用于判断是不是证书的锅）

### ⑤ `status` 显示 `SUCCESS` 但我没看到换班

见第 2 节「一条必须知道的陷阱」：**`SUCCESS` 不代表换班成功。**

## 9. 为什么是「确认制」，以及关于自动询问的诚实交代

因为这个端点是**匿名可达的**——任何人拿到那个 URL 就能 POST 它。所以下发的任务**只可能来自你自己的确认**：

- 领任务端点的响应**只来自插件自己的队列**，**不读请求里的任何字段**；
- 队列**只由你在 QQ 里发的 `/ak maa run` 填充**；
- **没有确认，队列永远是空的。**

**"响应与请求内容无关"**这一点有测试钉着（同一队列状态下，不同请求体必须得到同一个响应）。

**为什么一定要你去确认，而不是自动派**：MAA 每跑完一次就把班次索引**永久前进一格**。自动派意味着「插件以为该换班了」就等于「MAA 换了一班」——一旦插件算错时刻，**班次就跳错，而且写进配置不会自动纠正**。确认制把最后一步留给你，是**正确性**的一部分，不是多余的礼节。

### 「到点自动问你」已经做了（2026-09-29）

到换班时刻，插件会主动发一条：

```
【该换班了】第 1 班 从 09-29 08:00 开始。
要我让 MAA 在你电脑上跑一次吗？
要它跑 → 回 /ak maa run
你自己换 → 回 /ak maa skip

**不回就是「不跑」**：我不会催，也不会自己派任务——队列在你确认之前一直是空的。
```

几条要说清的：

- **它只是问，不是派**。自动询问与 `/ak maa run` 走的是**同一条派发路径**，而且自动询问**根本不碰队列**（有一条测试数 `enqueue` 被调了几次：tick 跑五次，零次）。你不回，什么都不会发生。
- **同一个换班只问一次**，重启也不会重问（"问过哪几次"是落盘的）。
- **它怎么知道换班时刻**：由「基建换班提醒」模块把**已校验的班次表**写进插件数据目录，本模块**只读**它。写入方**只有那一个**，所以「什么时候该换班」仍然只有一个来源——不是复制一份时刻（那份副本一旦漂移，插件就会在错误的时刻问你，你一确认班次就跳错）。
- **前提**：那个提醒模块要开着。关着就没这份表，`/ak maa` 的状态里会写明「还没读到」，**手动 `/ak maa run` 不受影响**。
- **通知目标**：你任意发过一次 `/ak maa`（哪个子命令都行）之后，它会记住那个会话并落盘，重启也不会丢。状态里会显示有没有目标。
- **宽限窗口**：默认「换班时刻过去 10 分钟内仍然补问一次」，用来兜住插件刚好在换班那一刻重启的情况。可在配置里改（`auto_ask_grace_minutes`），也能整个关掉（`auto_ask`）。
- **迟到了会说**：如果这条是重启之后才补上的，文案里会写「这条晚发了 N 分钟」，免得你以为时区算错了。

### 安全提示

- 端点是**匿名可达**的：**URL 泄露 = 别人能往里 POST**。不过任务只能由你的确认产生，所以即使 URL 泄露，别人也无法让 MAA 跑东西；但仍建议**不要把 URL 贴到公开场合**。
- **Key 会出现在** MAA 配置里、以及服务器 / 反代的访问日志里。
- 插件**只记请求体的形状**（键名、类型、长度），**不记内容**：你的标识、汇报数据都不会被写进日志。
- ⚠️ **一次换班只派一次**。这条由**插件自己**保证，不依赖 MAA 的承诺：同一次换班算出来的任务 id **完全相同**，而队列**只允许一个未结任务**，所以重复确认不会产生第二次执行，重试也是重发同一个 id。但**换一个新的任务就是新的一次执行**——那会让班次多跳一班。

**已经验证过的**（可以放心照做）：

- 两个端点的**准确路径**与**必须用 POST**（用 AstrBot 的真实路由匹配函数跑过）；
- **API Key 可以走查询串**（读了认证层源码并确认它接受 `api_key` / `key` 查询参数）；
- 协议要求领任务端点**必须回 `{"tasks": []}`**——官方原文「若不存在 tasks 则视为连接无效」，**不能省略字段、不能回非 JSON**；
- 汇报端点的**返回内容任意**——官方原文「MAA 不会读取返回内容，也不校验状态码」；
- **端点路径由服务方自定**——官方原文「端点路径随意」；
- MAA **只会传 `user` 与 `device` 两个字段**——官方原文；
- MAA 官方文档关于 `SUCCESS` 的那句原文（见第 2 节）；
- **2026-09-29 真机跑通**：`MaaWpfGui/v6.18.0` 连上公网端点，**每秒一次** POST `getTask`，服务器回 `{"tasks":[]}`（`200`，12 字节）；`reportStatus` 收到 `{"task","status","payload"}`. **自签证书那关通过后整条链路可用**；
- **任务体形状**（官方原文）：`{"id": "<唯一 id>", "type": "<类型>"}`；**「端点应当可以重入并且重复返回需要执行的任务」**、**「对于相同的 id，不会重复执行」**——插件的去重设计建立在这两句上。注意这两句只覆盖「**同一个 id**」；**跨 MAA 重启**那一条官方没说，见第 10 节第 6 项，**我们不依赖它**。
- **`LinkStart` 与 `LinkStart-Base` 的区别**（官方原文）：前者是「启动一键长草」（整套），后者是「立即根据当前配置，**单独执行**一键长草中的对应子功能」。插件默认用 `LinkStart`。
