### 模块如何取得自己的配置（C3 裁决）

**决定：`initialize(self, ctx, config)`——宿主把「该模块自己那一段」显式传入。**

```python
async def initialize(self, ctx: Any, config: Mapping[str, Any]) -> None: ...
```

理由：① 显式传参，不给 `Module` 加可变状态；② 模块只看到自己那段（`config[module.config_key]`），**不知道别的模块段存在**；③ 假模块在测试里直接收 dict 即可。宿主侧 `start_all(ctx, config)` 按 `config_key` 取段后传入。

### S5 硬性完成判据

**S5 在任何子命令落地之前必须先有指令权限过滤**——`/ak status` 会输出排班与绑定目标，`/ak bind` 会改掉推送目标。默认开放一旦成为事实标准就难收回。这是完成判据，不是待办。

**权限模型（2026-09-29 修订，替换最初的「只认已绑定会话」）**：

| 子命令 | 私聊 | 群聊 |
| --- | --- | --- |
| `bind` / `status` / `test` | **无条件允许** | **仅 AstrBot 管理员** |

修订原因：最初写成「只有已绑定的那个 umo 才能操作，例外是尚未绑定任何人时」，**逻辑上留了死锁**——「改绑」的前提就是换一个会话，而门禁只认原会话，于是用户一旦绑定就永远改不回去；若原会话那个号掉线，功能彻底锁死。同时它**防错了对象**：私聊里 `bind` 的语义是「我想收提醒」，只影响发起者自己，无风险；真正该防的是**群聊**（群里 bind 会把提醒推给全体成员）。**过度限制与完全放开一样，都是设计缺陷。** 判定实现为纯函数 `command_allowed(command, *, is_group, is_admin)`，便于单测覆盖真值表。

**效率 / 产出计算明确不做**（2026-09-29 逆向评估，见 `docs/project-plan/06-efficiency-assessment.md`）：参考站把它做成**服务端求解器**，前端产物里没有任何干员技能数据；自己实现要从零维护约 2,000 行技能表 + 一套连 PRTS 都承认未定论的叠加规则，还要拉入玩家练度与森空岛当前进驻两个外部依赖。**用户本身也已把这件事分配给那个网站**——重复造它等于制造两个会说不同话的权威。唯一保留的可能增量是**电力预算校验**（须诚实命名为"可行性检查"而非"效率"）。

### 铁律：森空岛失效绝不许拖垮核心功能（今晚的教训）

`skland` 的数据全部来自森空岛，而今晚实测它的凭据会失效、QQ 客户端会崩、接口会不通。因此：

1. **核心换班提醒（`shift_reminder`）必须能在 `skland` 完全失效时照常工作**——两者之间不许有依赖。
2. `skland` 自身失效时要**显式告知用户**（授权过期就提示重新授权），不许静默什么都不做。
3. `skland` 的授权凭据存 `plugin_data/`（不进仓库、不进日志）。
4. **边界**：只用森空岛**官方接口**；签到属于官方提供的正常操作。**不做任何绕过、模拟客户端、自动操作游戏的行为**——这条与立项时的「不碰游戏账号」一致。

### 模块与宿主的关系

新增模块一律遵守既有契约（`docs/architecture/extension.md` §2）：实现 `initialize` / `terminate`，可选 `apply_config` / `handle_command`；在 `_conf_schema.json` 的 `modules` 段加独立开关；**宿主不认识它们是什么**。

### 第二模块落地后做的两处地基改造（2026-09-29）

`recruit` 落地时如实回报了两个结构问题，总监裁决两个都修——它们是**有了第二个模块才暴露**的，只有一个模块时看不出来。

**一、权限判定收敛到 `core/permission.py`。** 此前两个模块各写一份 `command_allowed`（契约禁止模块互相 import，所以先各留一份）；但**权限规则有两份副本，就意味着改模型会漏改一处，那是一个安全洞**。现在规则只有一份 `session_allowed(*, is_group, is_admin, action)`：规则在 core，**文案由调用方通过 `action` 提供**（各模块做的事不同，一句笼统的「权限不足」对用户没有帮助）。`core/**` 是纯逻辑层，所以它只收布尔入参、不接收 event——「是否群聊／是否管理员」仍由装配层从事件上取。

**二、宿主逐模块隔离 `initialize` 失败。** 此前是「任一模块失败 → 回滚全部模块 → 插件整体加载失败」，等于**一个数据源挂掉拖垮整个插件**。现在单个模块失败只记进 `failed_modules`（**含原因**）并继续启动其余模块；宿主把失败逐条写 ERROR，并在 `/ak` 的兜底回复里告诉用户「哪个模块没了、为什么」。

- 这是「一个模块失效不许拖垮核心功能」那条铁律的**宿主层形态**：与其要求每个模块自己想办法「不抛异常」，不如让宿主本来就不怕某个模块抛。
- **零模块成功时插件仍然起来**：宿主 + `/ak` 指令本身有价值——它能告诉用户「模块都挂了」，比整个插件消失、用户一无所知要好。
- `Exception` 才被隔离捕获，**`BaseException` 不吞**（取消、退出信号会被当成「这条路不行」而吞掉，那更糟）；仍保留回滚，但只针对 `BaseException`。

> **页面与提醒对「不动」房间的取舍刻意相反**：提醒里**不渲染**（那是给用户的**指令**，照着一间不该动的房去换是错的）；页面上**必须显示并标注**（那是给用户的**全貌**，藏起来用户会以为我们读漏了），但**视觉上弱化**（降透明度 + 徽标，不用删除线——删除线读起来像「数据坏了」）。同一个数据、两种场合、两种取舍。

> **图标用中文房型名的首字**（贸/制/电/宿/控/会/办/加）做成徽章：不引图标字体、不依赖任何外部资源，也**永远不会与数据漂移**。

**关键设计决定：不从排班表解析班次时长。** 两个理由：① 班次时刻**本来就由用户在插件配置里填**（`shifts`），时长不需要文件提供；② riic.autos 导出与 MAA `custom_infrast` 的 `plans[].name` 写法不同（实测 MAA 样本是「12H第一班」，riic 导出据记录是「Shift 1 · 12h」），靠名字解析时长既脆弱又没必要。**解析器只认 `plans[].rooms[].operators[]` 一件事**，班次与 `plans` 按顺序对应。

**样本来源**：开发机上 MAA 自带的 `resource/custom_infrast/*.json`（20+ 个真实样本，与 riic 导出同源结构）作 fixture；用户手上的 riic 导出文件待其提供后补一轮验证。

**实测发现与裁决（2026-09-29，来自 V1.5.1 对 6 份真实样本的统计）**：

| # | 实测事实 | 裁决 |
| --- | --- | --- |
| 1 | `rooms[].skip` 字段真实存在且有 `skip: true`（18/340 条），其中 15 条**带着干员名**。MAA 语义 = **这一班这一间房不动** | **解析器照实保留 skipped 标记**（不丢数据），**渲染层默认不渲染**被标记的房间。理由：丢弃数据调用方看不见；但渲染进去就会告诉用户「去换这间房的人」——而排班表作者标明**不要动**，属**错误信息**而非冗余信息 |
| 2 | `plans[].name` 格式五花八门：`12H第一班`、`A+B 16H`、`1 7h`、`第1班`、`A 组 12 H`、`A+B 高效长班 1` | **更加印证「不解析时长」的决定**——名字格式根本不可依赖 |
| 3 | `operators` 为空是常态（29/340）；**无**条目缺 `operators` 键，也**无**非字符串/空串元素 | 「空 → 跳过该房间」是正常路径；过滤性分支仅作防御，真实数据不出现（测试仍要覆盖） |
| 4 | 样本含 4 班表（`*_4_times_a_day.json`，`plans` = 4），与固定三班的插件不匹配 | **`plans` 数量必须正好等于 3**，否则**导入失败并明确报错**（说明「这份表是 N 班，本插件是 3 班」）。**不许静默取前 3**——4 班表的班次安排与 3 班配置对不上，取了就是错数据 |

### V1.5.7 裁决：班次记「第 N 班」，不记人为标签（2026-09-29）

> 所有者原话：**「不要记夜班早班晚班，记第几班啊，用户导入根据自己的需求调整时间」**

**为什么这不是审美问题**：排班表的 `plans` 是**按位置**对应 `shift_i` 的（见 V1.5.1），而「早班/晚班/夜班」是**人为贴的标签**。用户一改作息，标签就与实际对不上，而插件**仍照着一个错的名字在做对应**。现场就是反例：所有者的排班表是 12/6/6，他自己的配置是 6/12/6——**"第 1 班"在两边不是同一班**，提醒里会显示另一班的干员，**而且全程不报错**。

因此做两件事：

1. **默认名改成位置名**（`第 1/2/3 班`），**默认时长顺序 12/6/6** 与 riic.autos 导出 / MAA 使用的顺序一致——顺序一致，"第 N 班"在两边才指同一件事。⚠️ **只改默认值，不动任何已有的用户配置**（那是运行时的事）。
2. **导入时把不一致说出来**：`roster.describe_duration_alignment(roster, configured_minutes)` 比对"表里的节奏"与"你配的节奏"，不一致时**指名道姓**列出对不上的班次。出口**复用回执的 `summary`**——页面的导入回执只渲染 `result.summary`，另起一个页面不读的字段等于没做。

**已知局限（已钉成用例，不许假装完备）**：两个**时长相同**的班次互换位置**测不出来**（12/6/6 里第 2、3 班互换后时长元组完全一样）。根因是**排班表的名字与配置的名字没有对应关系**，不能拿名字比。

**不做**：不拿排班表里的名字（`Shift 1 · 12h`，生成器给的）覆盖用户的班次名（给人看的）——两者用途不同。

> **同时更正一处旧口径**：上文 V1.5.1 的「靠名字解析时长既脆弱又没必要」写于**解析器**的立场，那句仍然成立；但 V1.5.6 起**会**从名字里读时长——**只作为建议、且不参与身份判定**。名字依旧不是班次的身份，**位置才是**。

**约束**：页面只是配置与状态的**另一种入口**，业务逻辑一律复用模块既有实现与 `core/**` 纯逻辑层，**不许在页面后端里重新实现一套班次计算**（否则两处逻辑必然漂移）。

**V2.2 前置结论：配置写回必须由宿主提供（2026-09-29 已核实源码）**

- 事实：`AstrBotConfig.save_config()` 在 `core/config/astrbot_config.py:262`（异步版 `:274`）；dashboard 另有 `PUT /plugins/config`（`dashboard/api/plugins.py:735`）。
- 但**模块拿不到 `AstrBotConfig` 对象**：C3 裁决规定「模块只拿到自己那一段配置」，而取出来的子 dict **没有 `save_config` 方法**。所以模块**无法**自己把配置写回去。
- **裁决**：把「配置写回」定为**宿主级基础设施**，不是业务功能。宿主 `main.py` 注册一个通用写回路由 `POST /{plugin_name}/config`，接收形如 `{"shift_reminder": {...}}` 的片段并合并保存。模块与页面都通过它写配置。
- **为什么不改 `initialize()` 签名加回调**：契约刚冻（第二次修订），为一件宿主本就能做的事再动地基不划算。
- **为什么不算破坏「宿主不认识功能」**：宿主只知道「配置」这个概念，**不知道「三班」是什么**；业务路由（如 `/{plugin}/shift-reminder/status`）仍由模块自己注册。
- **待实测**：改完配置是否需要重载插件才生效（页面改完若能即时生效最好，否则页面要明确提示「已保存，重载后生效」——**不许做成「存了但没生效」还假装成功**）。

**V2.2 附加结论：`save_config()` 只保证「内存 + 磁盘都更新」，不保证「运行中的调度跟着变」（2026-09-29 读源码）**

`save_config(replace_config)` 的实现在 `core/config/astrbot_config.py:262`：先 `_prepare_config_snapshot()`（内部 `self.update(replace_config)` **改内存**）再 `_write_config_snapshot()` **写盘**。也就是说调用它之后，配置对象本身是对的。

但**本模块是在 `initialize()` 里一次性读配置的**，已经注册进 `cron_manager` 的三个任务不会因为配置对象变了就自动改时刻。**光调 `save_config` 会得到「面板显示新值、提醒仍按旧时刻」这种最难查的错。**

因此 V2.2 的完成判据必须包含：**保存后由模块自己重新读取配置并重建定时任务**（复用 `initialize()` 里那段「按前缀清理旧任务 → 按新配置注册」的逻辑，正好它能幂等重入），页面回执要能反映「已生效」而不是「已保存」。**若做不到即时生效，就明确提示需重载——同样不许假装成功。**

## 2.7 MAA 到点自动询问与跨模块共享班次表（0.6.0）

> **触发**：2026-09-29 用户决定关掉 MAA 自带的定时器，改由插件在换班时刻触发；随后要求「到点自动问你」也做出来。
> **它卡在哪**：`maa` 需要知道"什么时候该换班"，而班次时刻只存在于 `shift_reminder` 的配置段里，**宿主只给每个模块自己那一段**（C3 裁决）。

**裁决**：由 `shift_reminder` 把**已校验的班次表**写进插件数据目录，`maa` 只读。**写入方唯一**，因此仍是一个事实来源。

**否掉的两个方案**（理由是它们各自的代价更大）：

| 方案 | 为什么不做 |
| --- | --- |
| 在 `maa` 段再要一份班次时刻 | 同一事实两份实现。**两份不一致时 `maa` 会在错误时刻触发，而 MAA 每跑一次班次索引永久前进、不会自动纠正**——本项目已为"同一个事实两处实现"栽过两次 |
| 宿主注入共享视图（给 `Module` 加 `wants_shift_schedule` 之类的开关） | 那是**为模块间通信造新机制**。本方案复用已有的用户数据目录，不新增通信原语 |

**这一版刻意保留的两处"看似不一致"，都是对的**：

- `autoask.due_boundary` 与 `core.shifts.boundaries_between` 对「正好等于现在」给**相反**结论——前者认"刚刚开始了一次换班"，后者找"下一次"。**把它们改得一致会造出真 bug**，两处都有注释。
- 询问的去重（`_asked`）与派任务的去重（队列的两条不变量）**是两套东西**：前者是"别重复问"的礼貌，**防多跑一趟的是队列不变量**。不要拿前者当安全机制去加固。

**明确保留的已知局限**：手动 `/ak maa run` 的任务**不与换班绑定**（走分钟粒度的 slot），所以同一次换班内隔一分钟连发两次仍会产生两个任务。更严的方案需要一份跨请求的"当前未结边界"状态，**而那份状态一旦泄漏到下一次真正不同的换班，结果是第二班静默不跑**——比"可能多跑一次"更坏。**主动选择保留宽松，而不是引入一个会静默漏掉的严格。**

**一条与它相关的实现约定**：`maa` 的巡检任务在模块开关关闭时**也会注册**，因为用户在面板上打开开关走的是 `apply_config`、**不会重新注册定时任务**；按开关决定注不注册，会让状态页写着"已开启"而实际没有东西在跑——**那是一句假话**。
