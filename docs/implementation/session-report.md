## 3. 过程中发现的关键问题（都值得留档）

**① 「保存成功」不等于「生效」**（读源码发现）

`AstrBotConfig.save_config()` 只保证**内存与磁盘**更新，**不会**让已经注册的定时任务跟着变。而模块是 `initialize()` 时一次性读配置的——页面改完班次只回一句「已保存」，用户会看到**面板显示新时刻、提醒仍按旧时刻跑**。这类 bug 每个环节单看都正常，最难查。处置：模块加 `apply_config` 钩子、保存后重建任务，页面回执反映「已生效」。

**② 校验失败的路径比成功路径更该想清楚**（子代理发现，我未预料）

业务校验在模块侧，而配置此时**已经写盘**。若 `apply_config` 因非法配置抛错，那份坏配置会**永久留在文件里，下次启动直接加载失败**。处置：apply 失败时把旧值**写回**——「宁可多写一次盘，也不要留下坏配置」。

**③ 班次顺序的坑**：`ShiftTable.shifts` 按开始时刻排过序（夜班 02:00 跑到最前），而排班表 `plans` 按第 1/2/3 班编号。直接按顺序取会**对错班**，必须用配置的原始顺序映射。

**④ `skip` 字段是真陷阱**：排班表里 `skip: true` 的房间**带着干员名**，但语义是「这一班这间房不要动」。渲染进提醒就是**错误指令**——不是冗余信息，是让人去改一间不该改的房。

**⑤ 许可证**：MAA 是 **AGPL-3.0**。子代理拒绝把 MAA 的真实样本复制进本 MIT 仓库作 fixture（会传染），改为按结构自撰。**格式与结构不受版权保护**，内容自写。这个判断比任务包本身更严谨。
