## 1. V1 实际交付了什么（集成的起点）

宿主是「工具箱」，`shift_reminder` 是第一个模块。宿主**不认识三班**——加新模块只需在 `modules/` 下放一个目录，注册表自动发现，老代码一行不改。

已交付能力：

| 能力 | 说明 |
| --- | --- |
| 三班模型 | 班次名、开始时刻、时长；**合计必须恰好 24h 且首尾相接**，否则拒绝加载并指出断点 |
| 定时提醒 | 每班注册一个 cron 任务，提前量可配（默认 10 分钟） |
| 推送 | 到点推送到已绑定会话；含当前班次、即将班次、换班时刻 |
| 幂等 | 同一班次的同一次换班只推一次，**重载不重复** |
| 熔断 | 连续失败达阈值后暂停推送（不刷屏） |
| 持久化 | 绑定目标 + 幂等键（JSON）、发送记录（JSONL，保留最近 50 条） |
| 指令 | `/ak bind`、`/ak status`、`/ak test`；权限＝**私聊放开、群聊限管理员** |
| 模块开关 | `modules.shift_reminder`，默认开；关掉不注册任何任务 |
| 测试 | 167 条，全部纯逻辑、不依赖 AstrBot 运行时 |

**关键约束（不可破坏）**：`core/**` 与 `modules/*/` 下的纯逻辑文件**禁止 import astrbot**（由 ruff 的 TID 禁入规则强制）。新集成的取数逻辑必须落在纯逻辑层或装配层，不能污染核心。

## 2. 候选集成项与许可证核验结论

| 候选 | 做什么 | 许可证结论 | 实施方式 |
| --- | --- | --- | --- |
| **riic.autos 排班表导入** | 从用户导出的 JSON 取出「每个房间放谁」 | 用户自有数据，无许可问题 | 自己写解析器，纯逻辑、可单测 |
| **WebUI 页面** | 改三班、看倒计时、看发送记录 | 骨架参考 `angel_heart`（已装插件） | `pages/` + `register_web_api` |
| **森空岛基建状态** | 读干员疲劳（心情）→ 真·按需换班 | ⚠️ **只抄 MIT**：`Morizero1125/astrbot_plugin_arknights_skland`（已有 `amiya building` 基建查询）、`Siq5005/astrbot_plugin_arknights`（`core/skland.py` 纯函数更工程化）。**避开**无 LICENSE 的 `Azincc/astrbot_plugin_skland`（README 自称 MIT 不构成授权） | 化用 MIT 代码或按其思路自实现 |
| **MAA 远程触发** | 到点确认后让本机 MAA 跑一次换班 | ⚠️ `astrbot_plugin_maa` 是 **AGPL-3.0，不能抄**。官方远程控制协议本身可用 | **自己实现** `/maa/getTask` + `/maa/reportStatus` 两个端点；**不 fork、不调它的私有方法** |
| ❌ 终末地相关 | 与本项目无关 | AGPL-3.0（`astrbot_plugin_endfield`） | 避开 |

**硬性红线**：不做「直接控制游戏账号」的事。森空岛只读取状态，不做自动化操作游戏。

## 3. 推荐顺序与理由

| 序 | 候选 | 为什么排这个位置 | 前置条件 |
| --- | --- | --- | --- |
| 1 | **riic.autos 排班表导入（V1.5）** | 纯离线解析、零外部依赖、**可以完整单测**；用户手上已有导出文件；把提醒从「该换班了」升级成「该换班了，把 X 换成 Y」——**信息量提升最大、风险最低** | 用户手动导出一次 JSON；确认导出文件的字段形状（实测：时长只出现在 `plans[i].name` 如 `Shift 1 · 12h`，**没有** `period`/`duration` 字段，需按名字兜底解析） |
| 2 | **WebUI 页面（V2）** | 现在改三班要手改配置项，体验差；页面骨架可参考已装插件，风险可控。**做完之后用户自己就能调班次，不用找我们** | `pages/` 与 `register_web_api` 在 4.28.1 已支持（已核实） |
| 3 | **森空岛基建状态（V3）** | 价值最高（**真·按需换班**，而不是按固定时刻），但需要扫码授权、涉及账号凭据，且要重新确认「不碰游戏账号」的边界 | 用户同意扫码授权；确认只读、不写操作 |
| 4 | **MAA 远程触发（V2+）** | 链路最长（服务器提醒 → 你确认 → 本机 MAA 跑），且**只能触发、不能选班次**；本机不常开机时价值打折。放最后 | 用户确认要不要这条跨机链路 |

## 4. 开工前需要用户定夺的问题

| # | 问题 | 影响 |
| --- | --- | --- |
| Q1 | 排班表多久变一次？要不要做成「导入一次长期用」 | 若经常变，导入功能的价值与自动化程度不同 |
| Q2 | 提醒里要显示干员名吗？还是只显示「该换班了 + 换谁」 | 决定 V1.5 的产出粒度 |
| Q3 | 森空岛那步，接受扫码授权吗？ | 决定 V3 是否可行（这是「按需」与「按时刻」的分水岭） |
| Q4 | MAA 那条跨机链路要不要？本机不常开机是否让它价值打折到不值得做 | 决定 V2+ 做不做 |

## 5. 每项的交付纪律（沿用 V1）

- 一次只做一个模块/子阶段，**垂直切片**，单次改动不超过一个小包
- 纯逻辑必须有单测；装配层不写单测但必须**部署后实测**
- 每完成一块：验证 → 提交 → 推送，**不攒堆**
- 上线后必测三条：加载零报错、真实推送到达、**重启后状态稳定**（V1 的三个缺陷全是上线后才暴露的）
