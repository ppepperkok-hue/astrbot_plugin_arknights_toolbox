## 1. 形态决策（v0.2 变更）

v0.1 定的是「独立小服务 + 直推 OneBot」。用户于 2026-09-29 改为「**直接做 AstrBot 插件**」，并要求插件**具备开发潜力**。

| 维度 | 独立小服务（v0.1） | AstrBot 插件（v0.2，采用） |
| --- | --- | --- |
| 发送通道 | 需要给 NapCat 加 HTTP 端点，**要改配置并重启容器** | 复用 AstrBot 已连上的两个 QQ 号，`context.send_message(umo, chain)` 直接发，**零运维改动** |
| 运行时 | 额外进程 / systemd 单元 / 容器 | 随 AstrBot 一起跑，无新增进程 |
| 配置界面 | 自己写配置文件，用户手工编辑 | `_conf_schema.json` → AstrBot WebUI 自动渲染设置表单 |
| 自定义界面 | 需要自己写前端 | `pages/` + `register_web_api()` → WebUI 内嵌页面，官方 bridge 已就绪 |
| 部署 | 独立部署 + 独立回滚 | 插件目录放进去、WebUI 点启用 |
| 代价 | 解耦，不怕 AstrBot 升级 | 与 AstrBot 版本耦合 → 用 `metadata.yaml` 的 `astrbot_version` 约束 + 只用官方公开 API 缓解 |

**结论**：插件形态在「省事」和「可扩展」两方面都更优，采用之。v0.1 的「否决 AstrBot 插件」决策被推翻，理由见 §7。

### 2.2 V2–V4 —— 本期只留扩展点，不实现

## 3. 业务规则

| 规则 | 说明 | 当前取值 |
| --- | --- | --- |
| 三班结构 | 12h + 6h + 6h = 24h，首尾相接 | 已定（用户口述） |
| 三班分界时刻 | **用户在插件配置里自定义**，给一组默认值兜底 | **可配置，默认 `08:00 / 20:00 / 02:00`** |
| 提前量 | 提醒早于换班时刻多久 | **10 分钟**（用户已确认），同样可配置 |
| 班次命名 | 用户可自定义叫法 | **可配置，默认 `早班 / 晚班 / 夜班`** |
| 配置校验 | 三段时长必须正好覆盖 24h 且首尾相接，否则拒绝启动并给出明确提示 | 设计约束（不静默猜） |
| 时区 | 固定 `Asia/Shanghai` | 已定 |
| 收件会话 | 提醒发到哪个会话 | 通过**绑定指令**记录 `unified_msg_origin`（用户确认发到自己的 QQ） |
| 提醒内容 | 本期不带干员名单 | 班次名 + 换班提示 + 下一班时刻（用户已确认） |
| 临时改班 | 今天不按表走怎么办 | 本期：改配置或关插件；不做自动推断 |

## 4. 范围边界

### 4.1 做（本期）

- 插件骨架：`metadata.yaml`、`main.py`、`_conf_schema.json`、`requirements.txt`（如需要）、README、LICENSE
- 配置项：三班定义、提前量、开关（走 AstrBot 配置系统）
- 三班校验（三段必须正好覆盖 24h，否则拒绝启动并提示，不静默猜）
- 换班时刻计算（含跨天）
- 收件会话绑定与持久化
- 定时调度 + 主动消息推送
- 消息渲染
- 幂等去重（重载/重启不重复）
- 手动测试指令、状态查询指令
- 失败重试与日志（走 AstrBot 的 logger）
- 为 V2/V3/V4 预留的模块边界（见 §2.2）

### 4.2 不做（本期非目标）

| 不做项 | 为什么不做 |
| --- | --- |
| 独立小服务 / 独立进程 / 容器 | 形态已变更，插件形态更省事（§1） |
| 自动操作游戏 / 调 MAA 自动换班 | 价值边界：只叫醒，不代打 |
| 网页 / 小程序前端 | 提醒终端是 QQ；将来要界面用插件 Pages，不另起前端 |
| 从 riic.autos 抓排班 / 需要登录的同步 | 无公开 API、需登录、不合规；V3 走**用户主动上传**导出文件 |
| 本期解析 MAA `custom_infrast` JSON | 排 V3 |
| 多用户 / 多账号 / 多游戏区 | 个人自用，单收件会话 |
| 读游戏内实时数据（森空岛心情） | 排 V4；且会触碰 01a §7「不碰游戏账号」，届时需重新判定 |
| 提醒回执（「已换」/「延后」） | 排 V3+ |
| 数据统计（漏了几次） | 无对应目标，砍 |

### 4.3 边界上的灰区（逐条判定）

| 灰区 | 判定 | 理由 |
| --- | --- | --- |
| 「疲劳驱动」要不要本期实现 | **不做** | 用户明确：疲劳是本质但不是硬约束，按周期提醒即可；只留策略接口 |
| 要不要顺手把 V2 的 WebUI 页也做了 | **不做** | 会拖慢 V1；只要 V1 的模块边界留对，V2 是加法 |
| 推送失败要不要加备选通道 | **不加** | 用重试 + 失败可见兜底，多一个通道多一份维护面 |
| 要不要「今天跳过」开关 | **本期不做** | 改配置能达到同样效果 |
| 要不要在消息里附 riic.autos 链接 | **不加** | 价值主张里没有「看排班表」，加了就是范围蔓延 |
| 插件要不要同时支持其他平台（Telegram 等） | **不做** | 只在 QQ 上用；但 `metadata.yaml` 里不写死平台限制，留余地 |

                                   │

                          │        v
