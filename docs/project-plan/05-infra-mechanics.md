## 0. 一句话结论

基建换班的真实机制是：**干员在工作房间持续消耗心情，心情归零后进入「注意力涣散」，其加成失效；宿舍以远快于消耗的速度恢复心情；而「什么时候换、换成谁」在游戏里需要玩家自己决定——但游戏已经自带了队列轮换与自动休整，缺的只是「到点了」这个触发。**

这句结论支撑了本插件的定位，详见 §9 与 §10。

## 1. 心情（疲劳）机制

### 1.1 上限与状态

**【权威】** 每名干员拥有**最高 24 点心情**。来源：[罗德岛基建（PRTS）](https://prts.wiki/w/罗德岛基建)。

工作区内的干员按心情消耗速率分为三种标识状态（同页）：

| 标识 | 含义 | 出现在哪 |
| --- | --- | --- |
| **工作中** | 心情消耗速率 **> 0** | 除加工站外的所有工作区设施 |
| **空闲中** | 速率 **= 0** | 加工站；或进驻于已停止工作的设施 |
| **休息中** | 速率 **< 0**（即恢复） | 通常为宿舍；也可能因技能出现在工作区 |

**【权威】心情归零 = 注意力涣散**：「无论进驻与否，心情耗尽（心情为 0）的干员将处于该状态。对于处于该状态的干员，**其后勤技能和基础效率在内的大部分加成会失效**，通常会对基建运行效率产生负面影响。」（同页）

> 注意措辞：**是「加成失效」，不是「房间停产」**。这一点很关键，见 §5。

### 1.2 工作区的心情消耗公式

**【权威】** 制造站与贸易站的「效用数据」给出**同一个公式**，仅符号写法略有差异：

- [制造站](https://prts.wiki/w/罗德岛基建/制造站)：心情消耗/时（默认值：`1 -X -Y`）
  - `X` = 基础心情消耗减免：按当前进驻人数，**1 名无减免（且不显示）、2 名为 0.05、3 名为 0.1**
  - `Y` = 干员后勤技能与**控制中枢**额外提供的心情减免之和
- [贸易站](https://prts.wiki/w/罗德岛基建/贸易站)：心情消耗/时（默认值：`1 +X +Y`）
  - `X` = 按处于工作状态的干员数：**1 名 0、2 名 -0.05、3 名 -0.1**
  - `Y` = 干员后勤技能与控制中枢额外提供的**群体**心情消耗效果之和

两个页面的注释都强调：**该计量表不计入「非群体」的心情影响**（如只作用于自身的技能），所以**干员的实际消耗可能与界面数字不同**。

**【权威】控制中枢的全局减免**：[控制中枢](https://prts.wiki/w/罗德岛基建/控制中枢) 的「全员心情消耗/时（默认值：`0 -X`）」写明——**每名处于工作状态的干员提供 0.05 的心情消耗减免**（该表反映的是「减免值」而非字面的「消耗/时」）。控制中枢进驻上限按等级为 1/2/3/4/5。

**由此可算出理论上限**（**【推测】**，但两条独立来源吻合）：

```
3 人工作站 + 控制中枢满员 5 人：
  1 − 0.1 − 0.25 = 0.65 心情/时
```

**【社区】** 这个 0.65 与一篇社区解答给出的数字完全一致（["生产位消耗 1-0.1-0.25=0.65 每小时"](https://www.9game.cn/wenda/1195621.html)）。**PRTS 公式与社区实测数字交叉验证通过**，我认为该值可信。

### 1.3 一个容易被忽略的量：界面倒计时

**【权威】** 贸易站页面有一个「干员信息：**倒计时**」，说明为：「显示干员以自身当前剩余心情和心情消耗速度下，**进入注意力涣散状态的理论所需时间**」（并注明未纳入消耗速度变动，可能与实际不符）。

**这意味着：游戏本身已经告诉玩家「这个干员还有多久涣散」。**

### 对插件的含义

1. **不要自己发明心情数值**。若将来做心情相关功能，公式就在上面，但**优先级低于**先把「要不要做」想清楚（见 §10 差距分析）。
2. **「涣散」不是停产而是降效**——这决定了提醒的紧急程度：晚十分钟换班，损失的是**效率**，不是**产出归零**。把提醒写成「紧急！要停产了」是**夸大**。
3. **游戏已有倒计时**，所以「这个干员还剩多少心情」不是玩家的痛點——**玩家痛的是「什么时候该去点换班」**。

## 2. 宿舍机制

### 2.1 恢复公式（本节最重要的发现）

**【权威】** [罗德岛基建/宿舍](https://prts.wiki/w/罗德岛基建/宿舍) 的「效用数据 → 心情恢复/时」给出了**完整公式**，并明确分为两部分：

```
心情恢复/时 = 白色字 + 绿色字

白色字 = 1.5 + 0.1 × 宿舍等级
绿色字 = 0.0004 × 实际宿舍氛围 + 后勤技能加成
```

原文补充两点（同页）：

- 白色字部分**由宿舍等级决定**
- 绿色字部分**由宿舍氛围和干员后勤技能决定**
- 该计量表**不计入非全体恢复的后勤技能**（如只作用于单体的），因此宿舍内不同干员实际恢复速度可能不同

**按等级代入白色字**（**【推测】**，直接套公式）：

| 宿舍等级 | 白色字（基础恢复） |
| --- | --- |
| Lv.1 | 1.6 /时 |
| Lv.2 | 1.7 /时 |
| Lv.3 | 1.8 /时 |
| Lv.4 | 1.9 /时 |
| Lv.5 | 2.0 /时 |

**绿色字需要氛围值**：`0.0004 × 氛围`。例如氛围 3000 → 1.2/时；氛围 5000 → 2.0/时。

> ⚠️ **【未找到】** 我没有查到**各等级宿舍的氛围上限的具体数值**（该页的「建造与升级」表格在我抓取时被截断）。所以「一间满级满氛围宿舍到底恢复多少」这个数**我算不出来**，不编。**需要的话可以再抓一次该页的「建造与升级」小节。**

**【社区】** 一篇社区文章给出的实测恢复值为「**3 + 0.2 = 3.2 每小时**」（其中 0.2 来自群体恢复类技能干员），见 [9game 的问答](https://www.9game.cn/wenda/1195621.html)。用上式反推：3.2 − 0.2 = 3.0 = 白字 + 绿字 → 若宿舍 Lv.5（白字 2.0），则绿字 1.0 → 氛围 2500。**这个自洽性让我认为该社区数字大体可信**，但氛围值我无法确证。

### 2.2 宿舍技能的种类

**【权威】** 宿舍页列出了全部宿舍技能，量级与叠加规则很清楚（以下是几个有代表性的，原文见 [该页](https://prts.wiki/w/罗德岛基建/宿舍)）：

| 技能 | 效果 | 备注 |
| --- | --- | --- |
| 嗜睡（杜林） | **自身 −0.1**，全宿舍 **+0.25** | 「同种效果取最高」 |
| 慵懒（安比尔/杜林） | 自身 −0.1，全宿舍 **+0.2** | 同上 |
| 利他主义 / 大锅饭·β / 狮心王 / 提灯女神 / 冬将军 | 全宿舍 **+0.2** | 同上 |
| 倾听者 / 明星效应 / 偶像 / 沁人心脾 等 | 全宿舍 **+0.15** | 同上 |
| 小酌怡情（冰酿） | 未满心情成员**平均分配**总计 **+0.8** | 单/多干员分别取最高 |
| 头号陪练（摩根） | 推进之王对**格拉斯哥帮**成员额外 +0.3 | 限定 |
| 死前必做清单（响石） | +0.15，且**每宿舍等级**额外 +0.02 | 叠加后取最高 |
| 无瑕心·β（隐德来希） | +0.1，且**每个招募位**额外 +0.1 | 与办公室联动 |

**要点**：绝大多数是「全宿舍 +0.15 ~ +0.25」，且**「同种效果取最高」而不是叠加**。

### 2.3 菲亚梅塔（Fiammetta）——两个技能，机制特殊

**【权威】** 宿舍页列出菲亚梅塔的两个技能：

| 技能 | 效果 |
| --- | --- |
| **患难之交** | 进驻宿舍时，**如果自身为满心情**，则与当前宿舍**前一位进驻的干员互换心情** |
| **自律** | 进驻宿舍时，**自身心情每小时恢复 +2**，同时**无法获得其他来源提供的心情恢复效果** |

**【权威】** 她的「前一位进驻」如何判定，在 [罗德岛基建](https://prts.wiki/w/罗德岛基建) 页的进驻机制一节有专门说明：「菲亚梅塔技能『患难之交』**严格遵循进驻规则**选择『前一位进驻』的干员，即使『前一位进驻』的干员是上一次进驻时保留的。」

**【权威】** 另有一条与进驻顺序相关的机制（同页）：具有**单体**心情回复机制的宿舍技能（如波登可），其目标优先选择**最低心情值**的干员并**锁定**直至回满；且「若在全新进驻时，该干员的位置排列在剩余 4 人之前，则该干员将始终锁定 2 号位而不是整个宿舍中心情值最低的干员」。

### 对插件的含义

1. **宿舍恢复远快于工作消耗**（这一条我很有把握，见 §4 的算术）：意味着**在基建配置合理的前提下，心情几乎不是瓶颈**。因此「心情快没了才提醒」的模型**不成立**——真实场景里更常见的是「忘了点换班」而不是「换班来不及」。
2. **菲亚梅塔的机制依赖「进驻顺序」**，而顺序是 MAA 排班表 `sort` 字段与 `Fiammetta` 字段在管的事。**提醒里如果要显示换成谁，顺序信息不能丢**——这解释了为什么 MAA 单独给她一个字段。
3. **宿舍技能有「同种取最高」**，所以「多塞几个恢复干员」并不线性增益——任何「堆恢复干员」的建议都不要做。

## 3. 房间与编制

### 3.1 设施种类

**【权威】** [罗德岛基建](https://prts.wiki/w/罗德岛基建) 把设施分为三类：

**工作区**：控制中枢、发电站、制造站、贸易站、会客室、加工站、办公室、训练室
**非工作区**：宿舍
**特殊类**：活动室

各设施的「进驻人员上限」（**【权威】**，来自各设施页面的「建造与升级」表）：

| 设施 | 建造上限 | 进驻人员上限 | 来源 |
| --- | --- | --- | --- |
| 控制中枢 | 1（自动解锁、不可降级） | Lv.1→1 / Lv.2→2 / Lv.3→3 / Lv.4→4 / Lv.5→**5** | [控制中枢](https://prts.wiki/w/罗德岛基建/控制中枢) |
| 制造站 | 5 | Lv.1→1 / Lv.2→2 / Lv.3→**3** | [制造站](https://prts.wiki/w/罗德岛基建/制造站) |
| 贸易站 | 5 | Lv.1→1 / Lv.2→2 / Lv.3→**3** | [贸易站](https://prts.wiki/w/罗德岛基建/贸易站) |
| 宿舍 | — | 见宿舍页 | **【未找到】**（该页表格被截断） |
| 其他 | — | — | **【未找到】** |

> 用户曾指出「贸易站和制造站的数量不一定是一」——这个观察**在机制上完全成立**：两者的**建造上限都是 5**，具体建几间由玩家的布局决定。我早前用真实排班表实测过：243 布局是 **2 贸易 + 4 制造 + 3 发电**、153 布局是 **1 贸易 + 5 制造 + 3 发电**（详见 §3.2）。渲染层若假设数量固定，就是错的。

### 3.2 「243 / 153 / 333」这类命名指什么

**【社区约定】+【实测印证】** 这串三位数指**贸易站 / 制造站 / 发电站**的数量。

**我的实测印证**（不是抄来的，是解析 MAA 自带样本得到的房间计数）：

| 样本文件 | 贸易站 | 制造站 | 发电站 | 名称是否符合 |
| --- | --- | --- | --- | --- |
| `243_layout_3_times_a_day.json` | **2** | **4** | **3** | ✅ 完全对上 |
| `153_layout_3_times_a_day.json` | **1** | **5** | **3** | ✅ 完全对上 |

样本位于开发机 `D:\mrfzmma\resource\custom_infrast\`（MAA 自带，AGPL 项目，**只读参考、不得复制进本仓库**）。

其它常见组合（**【社区】**）：

- **252** = 2 贸易 + 5 制造 + 2 发电（见 [9game 的问答](https://www.9game.cn/wenda/1197192.html)）
- **333** = 3 贸易 + 3 制造 + 3 发电（**【社区】**；我手上的样本里没有 333，**未实测印证**）

> ⚠️ **【未找到】** 我**没有找到**官方对这套命名的定义——它是玩家社区的约定俗成。但 243/153 有实测印证，我认为可用。

### 对插件的含义

1. **房间数量必须动态渲染**。任何「每类一间」的假设都是错的。（这一条我们**已经踩过**：页面被误解成只会显示一间贸易站——实际是当时导入的测试样本里就一间。）
2. **「发电站」不可忽略**：它是三位数里的一位，且影响无人机充能速度（见 §7）。若将来做布局分析，不能只看贸易与制造。
3. **不要把 243 当成唯一的正确布局**。252/153/333 各有适用面（缺干员的人适合 153/252，干员多的人适合 243），**插件不应该暗示只有一种布局是对的**。

## 4. 为什么是三班、为什么是 12/6/6

### 4.1 诚实的第一句：【未找到权威推导】

我查了 PRTS、MAA 官方协议文档、以及多篇社区攻略，**没有找到任何一处说明「三班 12/6/6」是游戏机制的必然结果**。它是**玩家的排班约定**，不是游戏规定。

### 4.2 把能算的算出来

用 §1、§2 的公式（**【推测】**，基于权威公式的算术）：

| 量 | 值 | 依据 |
| --- | --- | --- |
| 心情上限 | 24 点 | 【权威】 |
| 最优工作消耗 | **0.65 /时** | 【权威公式】1 − 0.1（3人） − 0.25（中枢满员）|
| 宿舍恢复（社区实测值） | **3.2 /时** | 【社区】 |
| 消耗 / 恢复 比 | **约 1 : 5** | 【推测】算术 |

**这个比值是本节最重要的结论**：

- 在**没优化**的基建里（1~2 人房间、控制中枢不满、宿舍等级低）：消耗可能接近 1/时、恢复 1.6~2/时，比值约 **1 : 2**——心情是**真实瓶颈**，玩家必须频繁换班（社区流传的「上 19 休 5」就是这种场景下的经验值）。
- 在**优化后**的基建里（3 人房间、中枢满员、高等级高氛围宿舍）：**恢复速度是消耗的 4~6 倍**。24 点心情按 0.65/时能撑 **约 37 小时**，而宿舍 3.2/时回满只需 **7.5 小时**。

**如果这个算术成立，那么对优化后的基建来说，心情根本不是瓶颈，12 小时一换在「防止心情耗尽」这个意义上说不通。**

### 4.3 那 12/6/6 到底为什么存在？三个候选解释

**【社区】倾向性解释（我判断最可能）**：12/6/6 的目的**不是防疲劳，而是产出最大化**——它让**高加成干员**尽可能覆盖「值得覆盖」的时段，同时用**替补干员**填补低收益时段。所谓「一队人上 12 小时、另一队人接 6 小时+6 小时」，本质是**两套人马的排班**，而不是「一套人马上到累再休息」。

**【推测】次要因素**：

- **累积类技能会因重新进驻清零**（**【权威】**，见 §6）——换班本身是有代价的，不能太频繁。12 小时这个粒度可能是「不浪费累积加成」与「不让加成干员闲置」之间的折中。
- **贸易站的订单计时**（**【权威】**）：3 级贸易站赤金订单基础时长 4:36:00。12 小时约等于 2~3 个订单周期，**换班时机与订单结算对齐**可能更符合直觉。
- **信赖值**：干员在宿舍也会累积信赖（**【权威】** 控制中枢页提到基建副手每日获得额外信赖，说明基建设施与信赖相关）——轮换能让更多人吃到信赖。

**其它节奏适用于什么**（**【社区】**）：

| 节奏 | 适合 |
| --- | --- |
| 12/6/6（三班） | 干员多、追求极限产出；主流选择 |
| 8/8/8（三班） | 心情压力大的中小基建；换班时刻规律、**好记** |
| 4 班制 | 干员极充裕、可以更细粒度轮换；MAA 样本里确实存在 4 班表（`*_4_times_a_day.json`） |
| 上 19 休 5 | **未优化基建**的经验值，用以保证心情不溢出 |

> ⚠️ 上表的「适合」来自社区攻略与我的推断，**没有官方依据**。社区讨论参考：[NGA 基建中枢心情消耗问题](https://ngabbs.com/read.php?tid=31935545)、[NGA 宿舍心情回复机制研究](https://ngabbs.com/read.php?tid=19545150)。

### 对插件的含义

1. **我们的 12/6/6 默认值是「社区约定」，不是「机制推导」**。这一点必须在文档与面向用户的说明里说清——否则用户会以为这是插件算出来的最优解。
2. **三班不是唯一的**。4 班表真实存在（MAA 自带样本里就有两份）。**当前实现「`plans` 数量必须正好等于 3，否则导入失败」是一个明确的限制**，它诚实（会报错而不是静默取前三），但它**拒绝了一类真实存在的排班表**。
3. **既然心情不是优化后基建的瓶颈，「到点提醒」的价值来自「提醒你去点换班」而不是「提醒你心情要没了」**。这直接决定了催办文案的语气（见 §5）。

## 5. 换班的真实目的：心情归零会怎样

### 5.1 后果的具体形态

**【权威】** 心情归零 → **注意力涣散**：后勤技能与基础效率在内的大部分加成失效（[罗德岛基建](https://prts.wiki/w/罗德岛基建)）。

**【权威】** 由此连带的后果：

- 涣散干员**不被视为处于「工作状态」**（同页）→ 因此**不提供基础效率**。制造站页面写明「基础生产力加成：**每进驻 1 名非注意力涣散的干员获得 1% 的基础加成**」——涣散会让这 1% 拿不到。
- **贸易站**页面的「干员信息：倒计时」直接把这个后果量化为一个时间（见 §1.3）。
- **控制中枢**的「全员心情消耗减免」也是「每名处于**工作状态**的干员提供 0.05」——所以**中枢里有人涣散，全局减免会下降**，进而**加速其他房间的消耗**。这是一个**连锁反应**。

### 5.2 不会发生什么

- **不会停产**：制造站/贸易站不会因为有人涣散而停止计时或清空进度。（**【推测】**，因为 PRTS 没有任何「停产」字样，只写「大部分加成失效」）
- **不会影响其它房间的产出**（除了上面说的中枢减免连锁）。

### 对插件的含义

1. **文案必须准确**：说「要停产了」是**错的**；说「效率会掉，中枢减免也会跟着降」才对。这属于「不许把推测写成机制」的直接应用。
2. **紧急程度要克制**：涣散是可逆的（回宿舍就好），损失是效率不是产出。**提醒不该用告警语气**。
3. **不确定性**：实际损失多少百分比，取决于该干员的技能与房间基础加成，**插件算不出来**（要算就必须内置全部技能数据）。所以**不要给「损失 X%」这种数字**。

## 6. 技能与加成

### 6.1 基础效率与技能叠加

**【权威】** 制造站：「生产力（默认值：`1 +X +Y`），`X` = **每进驻 1 名非注意力涣散的干员获得 1% 的基础加成**，`Y` = 干员后勤技能额外提供的生产力加成」
**【权威】** 贸易站：「获取订单效率（`+X% +Y%`），`X%` = 每名处于工作状态的干员提供 1% 的加成，`Y%` = 干员后勤技能额外提供的效率加成」

**【权威】叠加规则**——PRTS 各技能描述里反复出现的限定语，就是真实规则：

- **「同种效果取最高」**：绝大多数同类技能**不叠加**，只取最大值（例：宿舍里所有「全宿舍 +0.15」的技能，同时上多个也只有 +0.15）
- **「叠加后的最终值同种效果取最高」**：技能内部先叠加（如「+0.15，且每级 +0.02」），**跨干员**之间再取最高
- **部分技能之间确实可以叠加**：贸易站页面给出了**实测观测**——「α级与 α 级同时进驻时存在效果叠加：累积工作达到峰值时，观测订单质量分布为 65% 4 赤金…数学期望 3.46」，并注明「**具体叠加模型暂不确定**」（**【权威】承认不确定**）

> 这条「具体叠加模型暂不确定」很珍贵：**连 PRTS 都承认某些叠加规则没有完全搞清楚**。任何宣称能精确计算产出的工具都值得怀疑。

### 6.2 累积类技能与「重新进驻清零」

**【权威】** 两条相关的清零规则：

1. **需要时间达到封顶值（暖机）的技能，在换位时会被重置**（因为重新进驻了）——[罗德岛基建](https://prts.wiki/w/罗德岛基建)
2. 贸易站：「持有相关贸易站技能的干员**离开贸易站重新进驻/工位改变时，累积工作时间清空**，重新开始计算出现概率加成」——[贸易站](https://prts.wiki/w/罗德岛基建/贸易站)
   - α 级技能需累积工作 **3 小时**达到峰值，β 级需 **5 小时**

**【权威】** 这解释了 MAA 排班表里 `sort` 字段的存在：MAA 文档原文写「当使用稀音、帕拉斯、巫恋等干员且 `sort: false`，**干员顺序可能会被打乱，导致暖机效果丢失**」。

### 6.3 特殊订单

**【权威】** [贸易站](https://prts.wiki/w/罗德岛基建/贸易站) 页面列出 5 种特殊订单（佩佩的特别独占订单 4:30:00 固定、可露希尔特别订单 2:24:00、U-Official 的尤里卡订单、但书的违约订单、龙舌兰的订单），各有优先级：「一份订单仅可变为一种特殊订单」。

### 对插件的含义

1. **绝不要尝试自己算产出**。叠加模型连 PRTS 都标「暂不确定」；我们内置的干员数据里**没有技能数值**，算出来的任何数字都是编的。
2. **「换成谁」的价值 > 「该换了」**，但**「谁该换进去」的正确算法可能只有 MAA 有**（它内置了完整技能库）。所以**提醒里给干员名单是对的**（直接读排班表），**自己推荐替换人选是危险的**。
3. **换班有隐性成本**（暖机清零、累积清零）。所以**频繁提醒可能有害**——如果用户在订单周期中间被打断去换班，反而损失累积加成。**「提前多少分钟提醒」这件事本身值得重新想**（见 §10）。

## 7. 特殊机制

### 7.1 控制中枢

**【权威】** 三重作用（[控制中枢](https://prts.wiki/w/罗德岛基建/控制中枢)）：

1. **等级决定**基建区域开放程度与部分设施的最高等级
2. **进驻干员 → 全基建工作心情消耗减少**：每名处于工作状态的干员 −0.05（上限 5 人 = −0.25）
3. **技能是全局性的**：例如「所有制造站生产力 +2%」「所有贸易站订单效率 +7%」等（页面技能表大量实例）
4. 另外：任命**基建副手**每日获得额外信赖，**但「任命副手并不视为进驻基建」**

### 7.2 菲亚梅塔

已在 §2.3 详述。补充 **【权威】** MAA 协议文档给她**单独一个字段**（`Fiammetta.enable/target/order`），且 `target` 需要传入对应客户端语言的干员名（用 OCR 识别）。这印证了她在排班里是需要**特殊编排顺序**的角色。

### 7.3 其它设施的特殊性

**【权威】** 来自各设施页面与总览：

| 设施 | 特殊之处 |
| --- | --- |
| **加工站** | 进驻干员处于**「空闲中」**（不消耗心情）；可在加工时概率获得副产物。**它是瞬间结算类设施**，控制中枢的「全员心情消耗」表**不含**它 |
| **训练室** | 训练位上的干员有专门的**「训练中」**标识；协助位可缩短专精时间 |
| **会客室** | 加速线索收集、每日额外线索；**线索搜集速度**可被中枢技能提升（如祐天寺若麦的 +5%） |
| **办公室** | 提供**公开招募栏位**与标签刷新次数；**与宿舍技能联动**（如隐德来希「每个招募位额外 +0.1 恢复」） |
| **发电站** | 决定无人机**充能速度**（[罗德岛基建](https://prts.wiki/w/罗德岛基建)：通常 6 分钟/架，受发电站影响提升）；全部清理后可持有最多 **235 架** |
| **宿舍** | 见 §2；有**锁定编辑**（见 §9） |

### 7.4 无人机

**【权威】** 无人机可用于设施建造/升级；控制中枢 Lv.3 解锁「无人机协助」（消耗无人机加速制造与订单）；Lv.4 解锁「急速充能」（**1 理智换 2 架**）；充能通常 **6 分钟/架**，**超过上限的部分会被丢弃**（不会暂停充能）。

### 对插件的含义

1. **无人机是「有时限的资源」**（溢出的部分直接丢弃），这其实是一个**比换班更值得提醒**的对象——但它需要读游戏状态才知道当前持有量，**属于 V3（森空岛）范畴**。
2. **不要提醒去动加工站/训练室**——前者不消耗心情，后者是独立的专精队列，与换班无关。

## 8. MAA 的基建排班实现（官方协议）

**来源**：MAA 官方文档 [基建排班协议](https://docs.maa.plus/zh-cn/protocol/base-scheduling-schema.html)（**权威**）。

### 8.1 字段语义（逐条，取自官方文档）

| 字段 | 官方说明 | 对换班的实际作用 |
| --- | --- | --- |
| `title` / `description` | 作业名、描述，可选 | 展示用 |
| `plans[].name` | 计划名，可选 | 展示用 |
| **`plans[].period`** | 换班时间段（如 `[["22:00","23:59"],["00:00","06:00"]]`）。「若当前时间在该区间内，则自动选择该计划」；**若不存在该字段，则每次换班结束后自动切换为下一个计划**。文档原文明确：「**core 不处理该字段，若您使用接口集成 maa，请自行实现该逻辑**」 | **⚠️ 2026-09-29 更正（详见 `10-maa-shift-switching.md`）：不要把「core 不处理」读成「该字段无效」。** core 不处理是因为 **GUI 替它处理**——GUI 读 `period` 算出计划索引，再把索引（`PlanSelect`）交给 core。**没有 `period` 时，MAA 每次换班跑完会自动把索引前进一格**（官方协议原文），而该机制**对本项目所有者是生效的**（他的文件里 `period` 出现 0 次）|
| **`plans[].duration`** | 「工作持续时长（分钟），**保留字段，目前无作用**。以后可能到时间了弹窗提醒该换班了，或者直接自动换了」 | **MAA 自己也没实现时长驱动的换班** |
| `plans[].Fiammetta` | 为哪位干员使用菲亚梅塔：`enable` / `target`（OCR 识别，需客户端语言干员名）/ `order`（`pre` 或 `post`） | 菲亚梅塔的互换心情需要单独编排 |
| `plans[].drones` | 无人机使用：`enable` / `room`（`trading`/`manufacture`）/ `index`（第几间，1–5）/ `rule`（保留字段，目前无作用）/ `order`（`pre`/`post`） | 无人机投放 |
| `plans[].groups` | 干员编组（`control`/`manufacture`/`trading` 可用） | 便于整组轮换 |
| `plans[].rooms` | **必选**。取值 `control`/`manufacture`/`trading`/`power`/`meeting`/`hire`/`dormitory`/`processing`。**「缺少某个则该设施使用默认算法进行换班」** | **缺失 ≠ 这间房不存在** |
| `rooms[].operators` | 干员名数组（OCR 识别） | 换成谁 |
| `rooms[].sort` | 是否按 `operators` 顺序排序，默认 `false`。文档明确警告：`sort: false` 时**顺序可能被打乱导致暖机效果丢失** | 暖机相关，见 §6.2 |
| `rooms[].skip` | 是否跳过当前房间，默认 `false`。「**仅跳过换干员操作**，其他如使用无人机、线索交流等仍会正常进行」 | **这就是我们 V1.5 排查过的那个字段** |
| `rooms[].autofill` | 用原先算法自动填充剩余位置。若 `operators` 为空则该房间完全走默认算法 | |
| `rooms[].product` | 当前制造产物。识别到不符会在界面**弹红字提示** | |
| `rooms[].candidates` | 备选干员，「有谁用谁，选满为止」；**与 `autofill=true` 不兼容** | |
| `rooms[].use_operator_groups` | 为 `true` 时，`operators` 里的名字被解释为**编组名** | |

### 8.2 MAA 是「怎么决定该换班了」的？

**【权威】** 从协议文档可以确定的两点：

1. **MAA core 不处理 `period`**（时间窗），需要集成方自己实现选择计划的逻辑。
2. **`duration` 是保留字段、目前无作用**，文档设想的未来用途恰恰是「**到时间了弹窗提醒该换班了**」。

**【推测】** 因此 MAA 自身的换班触发依赖**它作为自动化工具的运行方式**（玩家启动 MAA 任务时执行一次换班流程），而**「什么时候该启动」是玩家的事**。

**这在机制层面证明了我们插件的存在意义**：MAA 官方文档把「到点该换班了」这件事明确标为**未实现、留给集成方**。我们做的提醒，正是补这一段。

### 8.3 `skip` 字段的真实语义（修正我们早前的理解）

**【权威】** 官方原文：「若为 true，其他字段均可为空。**仅跳过换干员操作**，其他如使用无人机、线索交流等仍会正常进行」。

这印证了我们 V1.5 的裁决方向是对的（`skip` 的房间不该在提醒里让人去换），但也说明**它不等于「这个房间完全不管」**——无人机与线索交流照旧。**我们的提醒只说「换谁」，所以跳过 `skip` 房间是正确的**；但若将来做「一键触发 MAA」，**不能把 `skip` 房间从整个计划里删掉**。

### 对插件的含义

1. **我们要实现的是 MAA 明确不做的那一段**——这是本项目最强的一条存在理由，值得写进 README。
2. **`period` 字段可以直接用来做「排班表自带的换班时刻」**，从而**免掉用户手填三班时刻**。这是一个**比现在更好的设计**（见 §10 差距 1）。
3. **`duration` 字段虽无作用，但官方设想的语义正是「提醒该换班了」**——我们的提醒与官方设想一致。
4. **`skip` 房间不能整间删掉**，只能跳过「换人」这一步。

## 9. 手动换班与自动化换班的差别

### 9.1 游戏自己已经能做什么（这一节改变了我的判断）

**【权威】** [罗德岛基建](https://prts.wiki/w/罗德岛基建) 的「批量编辑」一节（**揭幕者们**版本 2024/11/1 起）说明游戏内建了：

- **队列轮换**：对控制中枢、产出设施、会客室、办公室，玩家可预设**最多三个队列**并批量切换
- **快速切换**：自动从预设队列中挑一个应用，规则为「所有干员均未处于训练室训练位 ＞ **总心情比例最高** ＞ 队列序号靠前」
- **干员休整**：自动指定最多与宿舍空位相同数量的**未进驻且心情未满**干员，**按心情比例由低到高**送进宿舍；优先进驻氛围值高＞楼层靠上的宿舍
- **锁定编辑**（相见欢版本 2025/1/22）：宿舍可锁定位置，休整功能只在非锁定位置进行

**这是本节最重要的发现**：**「换成谁」游戏已经能自动做了**（快速切换 + 干员休整），而且它挑队列的规则比我们能做的任何推算都准确（它知道每个干员的真实心情）。

### 9.2 那玩家手动换班时到底在干什么

**【推测】** 基于上面的事实，玩家的动作其实是：

1. **想起来该换班了** ← **这一步游戏不提醒**
2. 进基建 →（点「队列轮换」应用预设队列，或逐个房间点）
3. 心情低的干员用「干员休整」送进宿舍
4. （可能）投无人机、收订单、线索交流

**容易忘的恰恰是第 1 步**。第 2~4 步游戏已经大幅简化了（队列轮换就是为此而生的）。

### 9.3 与 MAA 自动化的差别

- **MAA**：能自己登录游戏、识别界面、按排班表执行换班（OCR 识别干员名 + `skip`/`autofill`/`candidates` 等容错逻辑），但**它需要那台机器在跑，且需要你启动它**。
- **手动**：你人在手机上，随时能点，但容易忘。
- **我们的插件**：既不能操作游戏，也不该假装能；**它负责「提醒你该做第 1 步了」**，并把「该换成谁」抄给你（这样你即使不开 MAA 也知道怎么点）。

### 对插件的含义

1. **提醒的核心价值是「触发」**，不是「计算」。因为计算（谁该上）游戏和 MAA 都比我们准。
2. **提醒内容应该帮助用户「完成那几下点击」**，即：当前哪一班、该换成哪一套（干员名单）——这正好是我们 V1.5 已做的方向。
3. **我们不该做「一键帮你换」**（做不到），**也不该做「帮你算谁最该上」**（算不准）。**做不到的事不要承诺**。
4. **「提前 10 分钟」这个默认值值得重新考虑**：如果用户的动线是「看到提醒 → 打开游戏 → 点快速切换」，那提前 10 分钟是合理的缓冲；但如果他在上班，10 分钟可能反而更糟（提醒了他也点不了）。**建议把提前量设计成可配且解释清楚用途**（现在是可配的，这点没问题）。

## 10. 与现有实现的差距（本节最重要）

以下逐条对照**我们插件当前的设计假设**与**真实机制**。**这一节不回避问题。**

### 差距 1：班次时刻靠手填，而排班表里可能已经有时间信息（**设计缺陷**）

- **现状**：用户在插件配置里手填三个班次的开始时刻与时长，且**必须凑够 24 小时、首尾相接**，否则拒绝加载。
- **机制**：MAA 排班表的 `plans[].period` 字段就是**换班时间段**；而且 MAA 文档说 `plans[].name` 里常带时长信息（社区导出常见形如 `Shift 1 · 12h`）。
- **差距**：我们**舍近求远**——让用户把排班表里已有的信息再手抄一遍，还要自己保证算术自洽。
- **讽刺的是**：我们早前**主动决定「不从排班表解析时长」**，理由是正确的（`plans[].name` 格式五花八门、不可依赖，实测有 6 种写法）。**但 `period` 是结构化字段，不受该理由影响**——我当时没查 MAA 协议就下了结论，**这是一个基于不完整信息的决定**。
- **建议**：**导入排班表时优先用 `period` 填班次时刻**；用户手填作为回退。这能一次消掉「填时刻 + 凑 24 小时 + 首尾相接」三个门槛。

### 差距 2：硬性要求「正好 3 班」，而 4 班表真实存在（**限制过严**）

- **现状**：`plans` 数量必须**正好等于 3**，否则导入失败（诚实报错，不静默取前三）。
- **机制**：MAA 自带样本里就有两份 4 班表（`153_layout_4_times_a_day.json`、`243_layout_4_times_a_day.json`）；`duration` 字段的语义也不假定班次数。
- **差距**：**诚实但过于严格**——我们拒绝了一类真实存在的排班表。而且我们自己的文档（§3.2）也说布局有多种，那么班次数同理不该只有一种。
- **建议**：把「三班」放宽为「**N 班（N 由排班表或用户配置决定）**」。这是个不小的改动（配置结构、cron 注册、渲染都要跟着走），但**当前的 3 班假设是硬编码进产品设计的**，越早改越便宜。

### 差距 3：「心情耗尽前提醒」这个模型本身站不住（**定位需要修正**）

- **现状**：插件的默认叙述是「到点提醒你去换班」，默认场景是「三班制」。
- **机制**：
  - 优化后基建里，**恢复速度是消耗的 4~6 倍**（§4.2），**心情不是瓶颈**；
  - 游戏**自带宽高亮提醒**（贸易站页面的「干员信息：倒计时」告诉玩家每个干员还有多久涣散）；
  - 游戏**自带队列轮换与自动休整**，换谁上不用玩家想。
- **差距**：如果心情不是瓶颈、倒计时游戏会给，那么**「防止心情耗尽」不是真实痛点**。真实痛点是**「忘了去点那几下」**。
- **建议**：把定位从「疲劳管理」修正为「**换班时点提醒**」——强调「到点了、该换成这一套」，而不是暗示「不换就要减产」。**我们的文案现在有没有夸大？值得逐条审一遍。**（当前文案「10 分钟后换班」是准确的，属于好的那一类。）

### 差距 4：没有利用游戏已有的「队列」概念（**可增强**）

- **现状**：提醒给的是「这一班每个房间放谁」（一张平铺的房间→干员表）。
- **机制**：游戏的「快速切换」是按**预设队列**整体切换的；MAA 排班表也有 `groups`（干员编组）字段。
- **差距**：用户拿到的是一张表，而实际执行动作是「选一个队列」。**两者之间需要用户自己翻译**。
- **建议**：若排班表里有 `groups`，提醒可以按**编组**呈现（「把贸易站切成『古+银』组」），更贴近实际点击路径。**这是锦上添花，优先级低于差距 1/2。**

### 差距 5：`skip` 的处理是对的，但理由要补全（**已正确，文档待补**）

- **现状**：`skip: true` 的房间**不在提醒里渲染**（因为那会让用户去换一间不该动的房），但**页面上显示并标注**。
- **机制**：官方原文是「**仅跳过换干员操作**，其他如使用无人机、线索交流等仍会正常进行」。
- **差距**：我们的处理**正确**，但我们的文档把它理解成「不要动这间房」。更准确的说法是「不要换这间房的人」——**无人机与线索交流照旧**。
- **建议**：文档措辞修正；**将来若做「一键触发 MAA」，绝不能把这些房间从计划里删掉**，只能跳过换人。

### 差距 6：不确定性的表达（**小问题，但影响可信度**）

- **现状**：提醒与页面显示的干员名单来自排班表，这是**事实**（文件里就是这么写的），没问题。
- **机制**：但「这套排班是否最优」「换了之后能提升多少」**我们完全不知道**（PRTS 都承认叠加模型不确定）。
- **建议**：**永远不要给产出预估**。我们给的是「排班表说了什么」，不是「这样做多赚多少」。**保持这个边界。**
