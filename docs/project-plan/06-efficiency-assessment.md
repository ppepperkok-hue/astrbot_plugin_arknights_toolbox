> **本文件的性质**：只记录**学到了什么、代价是什么**。**没有复制任何代码或数据文件进仓库**；正文里出现的极短片段仅用于说明结构，出处已标注。
> **方法**：抓取该站 `/_next/static/` 下的**全部**前端产物（14 个 JS + 3 个 CSS，共约 1.1 MB）、`/manual` 的 HTML 与其 RSC 数据负载（105 KB），并对公开接口做**只读探测**（GET/OPTIONS）。
> **可信度标注**（同 `05-infra-mechanics.md`）：
> - **【实证】** = 我在抓到的产物或接口响应里**直接看到**的事实
> - **【推测】** = 基于实证的推算
> - **【未拿到】** = 查了但拿不到
> **核实时间**：2026-09-29。

## 0. 一句话结论

**它的效率计算是一个服务端求解器，不是前端脚本。**

前端（我们能拿到的那 1.1 MB）里**没有一位干员的 id、没有一张干员头像的 URL、没有任何一条基建技能的数值**。所有效率数字都是服务端算好后发给前端、前端只负责加总和格式化的。

**所以「照它的结果做一个」在技术上是可行的，但代价不是"抄一段公式"，而是"从零建一张干员基建技能数据库 + 一套连 PRTS 都承认没定论的叠加规则"。** 详见 §6 的三条路线对比与推荐。

## 1. 它的效率计算长什么样（Q1）

### 1.1 输入【实证】

前端在提交排班请求前会构造一个对象，字段名直接可见：

```
layout（整套设施布局）· operbox（干员练度箱）· rotation（换班方式）
fiammetta_enable（菲亚梅塔开关）· sourceType / boxSource / sourceName
```

**`layout` 的形状**（来自前端的校验与编辑函数）：`rooms[]`，每间房带

```
id · kind · level · product
```

其中 `kind` 的取值集合是：`control_center` / `trade_post` / `factory` / `power_plant` / `dormitory` / `office` / `meeting_room` / `workshop` / `training_room`；`product` 决定制造站的产物（`gold` 贵金属 / `battle_record` 作战记录 / `originium` 源石碎片）或贸易站的订单（`gold` 龙门商法 / `originium` 开采协力）。

**房间等级上限**：`control_center` 与 `dormitory` 为 **5**，其余为 **3**（前端函数 `maxRoomLevel`）。

**`operbox` 的形状**（来自公开的示例数据 `/api/sample-operbox`）——**这就是「练度」的定义**：

```json
{"id": "char_009_12fce", "name": "12F", "elite": 0, "level": 30,
 "own": true, "potential": 6, "rarity": 2}
```

- 该示例共 **429 位干员**（覆盖全部干员）
- `elite`：精英化阶段 0/1/2；`level`：等级；`potential`：潜能 1–6
- **`id` 用的是 `char_` 前缀的 charId——与 PRTS 同一套命名**，这一点很重要（见 §2）

页面文案里还有一条佐证：上传入口写的是「**上传练度 JSON / XLSX**」，且提示「支持的 MAA JSON 语言…」，说明它**能直接吃 MAA 的排班表文件**，并且**需要玩家自己的练度数据**。

### 1.2 输出与公式【实证】

前端有一个专门的归一化函数，把服务端返回的两套字段（新版/旧版）统一成一种内部形状。它接受的服务端字段包括：

```
final_efficiency · total_efficiency · order_multiplier
base_efficiency · equivalent_efficiency · global_efficiency
trade_equivalent_efficiency · gold_equivalent_efficiency
trade_efficiency · trade_skill_efficiency · trade_display_efficiency
manufacture_efficiency · manufacture_skill_efficiency · manufacture_display_efficiency
power_efficiency · power_skill_efficiency · power_display_efficiency
trade_score · trade_pct · trade_skill_pct · trade_display_pct · trade_gold_pct
manu_score · manu_prod_total · manu_prod_skill · manu_display_pct · manu_storage_limit
power_score · power_skill_pct · power_display_pct · power_charge_speed_pct
```

**主公式**（一个渲染函数，逐字可见；下面这段是极短摘录，出处为 `chunk03.js` 内的 room-efficiency 呈现函数）：

```
总效率 = base_efficiency + equivalent_efficiency + global_efficiency
```

它以 `×100` 显示，并把三项拆成 `= 基数 + 技能效率 + 跨设施`。**这正好对应所有者截图里的** `223.5% = 103% + 113.3% 技能效率 + 7% 跨设施`。

### 1.3 三个房型各有一套呈现【实证】

- **贸易站**：`总效率 = 100% × 综合加成 × 订单机制`
  - `综合加成` ← `trade_skill_pct`；多出来的 `跨设施` = `trade_display_pct − trade_skill_pct`
  - `订单机制` 是**乘法项**，由 `final_efficiency ÷ (综合加成/100)` 反算，或直接取 `trade_gold_pct`
  - 另有「等效 X% 技能效率」（`trade_equivalent_efficiency`）
- **制造站**：`总效率 = 100% + 纯技能 + 跨设施 + 综合加成`
  - `纯技能` ← `manu_prod_skill`；`跨设施` = `manu_display_pct − manu_prod_skill`
  - 剩余差额归为 `综合加成`；另有「**仓储上限**」（`manu_storage_limit`）
- **发电站**：优先显示 `final_efficiency`/`total_efficiency` 并标为「**总效率**」；否则
  - `充能效率` ← `power_skill_pct`（或 `power_charge_speed_pct`）；`跨设施` = `power_display_pct − power_skill_pct`
  - 另有「**总充能**」← `power_score`
  - 标签会依数据在不同来源间切换（有 `power_display_pct` 时叫「展示效率」）

### 1.4 概念定义（据上可推定）【推测，除标注外】

| 概念 | 含义 | 依据 |
| --- | --- | --- |
| **技能效率 / 纯技能** | 该房间内干员的**基建技能**带来的加成，扣掉了跨设施部分 | 由「display − skill = 跨设施」的差值关系推得 |
| **跨设施** | 来自**本房间之外**的加成（典型是控制中枢的全局技能、或其它设施的联动） | 名称为 `cross-station`/`global_efficiency`，且与前两项**相加**而非相乘 |
| **综合加成** | 无法进一步拆分的剩余加成（含基础效率与暖机等） | 在制造站分支里它就是 `总额 − 纯技能 − 跨设施` 的差值 |
| **展示效率** | 与「纯技能」并列的另一个口径，服务端同时给两个数，前端显示差值 | `display_pct` 与 `skill_pct` 同时存在时才出现跨设施项 |
| **仓储上限** | 制造站的容量上限（受设施等级与技能影响） | 字段名 `manu_storage_limit` |
| **预计日产物** | 按这套方案一天能产出多少（经验 / 龙门币 / 赤金 / 合成玉 / 源石碎片） | 页面文案 `estimatedDailyProduction`，且列出五种产物 |

**注意**：上面这些**是它怎么显示**。**这些数是怎么算出来的，前端完全没有**——前端只做加总与格式化。

### 1.5 一个诚实的边界：前端确实有一小块规则

前端**确实**带了一些设施规则，但都是**与干员无关**的：

- **发电预算**：发电站发电量 `{1:60, 2:130, 3:270}`；各设施耗电量按类型与等级一张表（如 `factory:{1:10,2:30,3:60}`、`dormitory:{1:10,2:20,3:30,4:45,5:65}`）；函数 `computePowerBudget` 返回 `{ok, generated, consumed}`
- **布局预设**：`243 / 333 / 252 / 342`（贸易/制造/发电数量）
- **MAA 产物名映射**：`Gold/贵金属 → gold`、`Battle Record/作战记录 → battle_record`、`Originium Shard/源石碎片 → originium`

**含义**：房间等级的硬规则、电力平衡、产物口径这一类**是公开且确定的**，可以自己实现；**干员技能那一层才是服务端的黑箱。**

## 2. 它依赖多少数据？（Q2 —— 最关键的一问）

### 2.1 结论先说：数据全在服务端，前端一条都没有【实证】

我把 14 个 chunk（1.1 MB）全文检索过，结果如下：

| 检索项 | 命中 |
| --- | --- |
| `char_` 开头的干员 id | **0** |
| 任何干员名 → id 映射（`charId`/`char_id`/`operatorId`） | **0**(`idMap` 8 次，但与干员无关) |
| 干员头像 URL 模板（`img/avatar`、`avatar/`） | **0** |
| 绝对 http(s) 图片地址 | **0**（22 个 http 链接全是框架文档、备案、许可证） |
| 干员名字（拿截图里的 13 个名字逐个查 `manual.html`） | **0**（仅「遥」1 次，是子串误命中） |
| `/manual` 的 HTML 里 `<img>` 标签 | **2 个**（都是页脚合作伙伴 logo） |

它**唯一的头像组件** `RemoteAvatar`（带 `fallback`/`loading`/`loaded` 三态、`referrerPolicy:"no-referrer"`）在全量产物里**只被使用了一次**——用在**森空岛账号头像**上，不是干员。

**结论**：干员数据、技能数值、头像地址，**全部由服务端在运行时给出**。前端的角色是：表单 + 校验 + 渲染。

### 2.2 它还依赖玩家自己的数据【实证】

- **练度箱**（`operbox`）：429 位干员的 `elite/level/potential`——**没有这个就算不了**（错误码 `AIC-BOX-1101`「干员练度数据无效」）
- **森空岛授权**：`/api/readiness` 返回 `skland.available: true`；产物里有 `/api/skland*` 代理端点，`skland` 出现 56 次
- `/api/workspace`、`/api/account/saved-plans` 未登录返回 **401**，说明有账号体系与云端保存

### 2.3 量级估计【推测，依据已写明】

**要自己实现同样的计算，需要长期维护的表：**

| 数据 | 量级 | 依据 |
| --- | --- | --- |
| 干员 | ≈ **429** | `/api/sample-operbox` 实际返回 429 条，即"全干员" |
| 基建技能条目 | ≈ **600–850** | 每位干员通常 1–2 个基建技能，少数 0 个或更多（**【推测】**；我未能从 PRTS 取到确切计数，见 §8） |
| 技能数值行 | ≈ **1,800–2,500** | 多数技能的效果**按精英化阶段（0/1/2）分档**，部分还随潜能变化 → 每技能约 3 档 |
| 房型/等级硬规则 | ≈ **40** 条 | 9 种房型 × 最多 5 级 + 电力表（**这部分前端就有，已知**） |
| 组合/协同规则 | **未知条数** | 服务端有 `combination_id` / `combination_name` / `conditions` / `efficiency` 字段，且页面有「设施组合提升空间」——说明它维护了**成组的干员搭配表** |
| 产物基数 | 5 种产物 × 各档位 | 要算「预计日产物」还需要订单/配方的基础产出与周期 |

**综合：最小可用的技能数据库在 2,000 行上下，外加一层连权威 wiki 都不敢定的叠加规则**（见 §3）。这不是"一张 JSON"，是一项需要**跟着游戏版本持续更新**的长期维护工作。

### 2.4 数据来源的替代路径【推测】

好消息是：**干员 id 与 PRTS 同一套（`char_` 前缀）**，而我们项目已经在用 PRTS 的公开 Cargo API（公招模块的数据就是这么来的）。所以**数据是"能拿到"的**——难点不在获取，在**规则**（§3）与**长期维护**（§6）。

## 3. 复杂度在哪？（Q3）

**【权威，引自 05-infra-mechanics.md】** PRTS 自己在贸易站页面写着「**具体叠加模型暂不确定**」——**连权威 wiki 都没完全搞清**。具体模糊地带：

1. **同种效果取最高 vs 相加**：PRTS 说多数技能是「同种效果取最高」，但**部分技能之间确实能叠加**，且没有完整的判定表
2. **跨设施的边界**：控制中枢的全局加成、宿舍技能与会客室的联动、办公室与公招栏位的联动——哪些算进「跨设施」、哪些不算
3. **暖机/累积类技能**：换位会清零（α 级 3 小时、β 级 5 小时达峰），所以**同一组人放不同时长收益不同**——这直接意味着效率**随时间变化**，不是一个静态数
4. **菲亚梅塔**：有专属机制（互换心情、屏蔽其它恢复），且被单独建模
5. **心情状态**：涣散干员的加成会失效，而心情取决于**整套排班的时间线**，不是单房间的静态属性

**这五条合起来意味着**：效率不是一个「输入配置 → 输出数字」的纯函数，而是**一个带时间维度的模拟**。它服务端有 `求解器`（solver）、**任务队列**（`taskQueue`）、**求解报错记录**（`solverErrorRecords`）、**迭代更新提示**（「求解器正在迭代更新」），这印证了它是个**迭代求解器**而不是一段算术。

**对插件的含义**：**这不是可以"顺便做一下"的功能。** 它和「到点提醒」不是一个量级的工程。

## 4. 「匹配率 45%」是什么？（Q4）

**它比较的是「你现在的基建」与「这套方案」，且不含宿舍。** 依据是页面自己的文案【实证】：

```
"rich1": "最接近第 {N} 班 · 匹配率 {P}"
"rich2": "需调整 {N} 处"
"nonDormitoryMatch": "非宿舍匹配"
"nonDormitoryFacilityMatchPercentage": "非宿舍设施匹配百分比"
"currentNonDormitoryAssignmentsMatchThisShiftExactly": "当前非宿舍进驻与排班完全一致"
"currentStateMatch": "当前状态匹配"
```

配套还有一张**逐房对比卡**，把差异按动作分组：

```
missing: 需换入 · unexpected: 需换出 · misplaced: 位置调整 · tired: 疲劳
```

**因此它对我们的含义很重**：匹配率**需要知道玩家"当前游戏内的进驻状态"**。它拿到这个的途径是**森空岛授权**（`/api/skland*` + `skland.available`）。

**我们如果做，就必须：** 要么让用户授权森空岛（多一条会失效的外部依赖，正是我们刚在 `05-infra-mechanics.md` §2.7 立过铁律要防的东西），要么让用户手动导入当前布局——而**手动导入"我现在谁在哪"对用户是很重的负担**。

**这是我们不该自己做匹配率的主要理由之一。**

## 5. 点击干员头像会发生什么？（Q5）

**结论：没有找到「点击干员头像 → 详情」这个交互。**【实证 + 未拿到】

- `干员详情` 0 次、`operatorDetail`/`OperatorDetail`/`opDetail` 0 次、`头像` 0 次
- `OperatorChip` / `operator-chip` / `op-avatar` 等组件符号 0 次
- 唯一的 `viewDetails: "点击查看详情"` 属于**排班结果摘要**（`scheduleResultSummary`），点开看的是**该班次的逐房详情**，不是某位干员
- 房型卡右上角那个按钮的真实用途是**反馈**，原文：**「求解器正在迭代更新，遇到 Bug 或问题可以点击对应房间右上角的反馈按钮」**

**⚠️ 但我要标明边界**：我可获取的是**该路由的**产物。若站内把干员详情放在**按需加载的另一条路由**里，我不会拿到。**我没能证伪它存在，只能说：在这条路由的全部产物里没有。**

**这对我们最有用的其实是否定结论**：所有者原本设想「点干员看详情」——参考站**没有做这件事**。它把交互预算花在了**班次切换**与**逐房对比**上，这与我们 U5 做的班次切换方向一致。

## 6. 如果我们要自己做，代价是什么？（Q6）

### 路线 A：完全自己做（自建数据表 + 自己推公式）

**要做的事**：建 2,000 行量级的技能表 → 实现叠加规则（其中若干条 PRTS 都未定论）→ 加时间维度的心情/暖机模拟 → 接玩家练度 → （若要做匹配率）再接森空岛。

**风险**：
- **会算错，而且是静默算错。** 一个错标的效率数字会被用户当成事实来规划。对比之下，公招模块算错「必出」我们已经视为不可接受——效率数字的后果更重
- 项目当前的性质是**一个人维护的 MIT 插件**，而这是一项**要跟版本持续更新**的长期负担
- 「迭代求解器 + 任务队列 + 报错记录」说明参考站的实现本身也不是一次算准的

**结论：不推荐。**

### 路线 B：只做「展示排班表已有的信息」，不碰效率计算（= 现状）

**现状**：我们已经能导入 MAA / riic 的排班表，展示每班每房放了谁，并在提醒里带上干员名单。

**我逐字核对过**：这两类文件里**没有效率数值**（riic 导出的 `plans[].rooms[].operators[]` 只有干员名；MAA 的 `custom_infrast` 同样没有）。**所以"免费拿来显示"这条路不存在**——不是我们偷懒，是文件里真没有。

**结论：推荐保持。**

### 路线 C：别做，引导用户去参考站

**做法**：在插件页面明确告诉用户「排班与效率计算请用 riic.autos」，我们的职责是**到点提醒 + 显示这一班该上谁**。

**与所有者已定的定位一致**：他原话是「**排班由用户上那个网站解决，这个网站就是在解决排班的效率**」。

**结论：推荐，且应当与 B 合并执行。**

### 推荐（明确结论）

**走 B + C：维持现状不做效率计算，并在插件页面显式把用户引向参考站。**

三条理由，按分量排序：

1. **数据与规则都不在我们手上**：前端的全部证据表明算法与数据在服务端；而规则层**连 PRTS 都写着「暂不确定」**（§3）。我们做不出"对"的版本，只能做出"看起来对"的版本。
2. **它需要玩家的练度与当前布局**：练度要靠用户导入（可观负担），当前布局要靠森空岛（会失效的外部依赖，正是我们刚立过铁律要防的）。**做了它会污染本项目最硬的那个优点——核心提醒零外部依赖。**
3. **所有者已经把这件事分配给别处了**：他自己说过排班的效率由那个网站解决。**我们重复造它，等于制造两个会说不同话的权威。**

### 一个"小而确定"的可选增量（若将来有余力）

**唯一我认为值得考虑、且边界干净的是「电力预算校验」**：发电量 vs 耗电量，规则是**定死的**（发电站 `{1:60,2:130,3:270}`，设施耗电按类型等级），**不依赖任何干员技能**，也不需要森空岛。用户导入布局后，我们能可靠地告诉他「这套布局电不够/够」。

**但请注意**：它是**可行性检查**，不是"效率"。**不要把它宣传成效率计算。** 而且它只是"可以考虑"，不在本次推荐范围内。

## 7. 授权提醒：哪些东西即使技术上拿得到，也不能进我们的 MIT 仓库

本项目是**以 MIT 发布到公开市场**的。据此：

| 对象 | 能不能进仓库 | 说明 |
| --- | --- | --- |
| 参考站的 **JS / CSS 代码** | ❌ **不能** | 授权是「仿照结果设计」，不含代码再分发，更不含以 MIT 再许可 |
| 参考站的 **布局预设数据**（243/333/252/342 的房间构成） | ⚠️ **谨慎** | 这些是**游戏事实**（社区通用叫法），社区共识部分可自行表述；**但它那份具体的 JSON 结构不要照搬** |
| 参考站的 **头像 CDN / 图片素材** | ❌ **不能打包** | 且**游戏图片版权属鹰角**（本项目 U6 已据此改为**外链 + 本地回退**） |
| **PRTS 的正文表述** | ❌ **不能复制** | PRTS 为 **CC BY-NC-SA**；只能取**事实性数值/规则**并注明出处（本项目既有做法） |
| **MAA 的实现代码** | ❌ **不能** | AGPL-3.0（本项目红线，见技术栈 C2） |
| **游戏内文案**（房型名、技能名、产物名） | ⚠️ **谨慎** | 名称属事实性引用，同人工具普遍使用；**但不要成段复制游戏文本** |
| 我们**自己算出来的**结论与自写实现 | ✅ 可以 | 这才是能进 MIT 仓库的东西 |

**一句话**：**能进仓库的只有"我们自己写的实现"和"公开事实数据"**。参考站给我们的应当是**信息组织方式与设计判断**（这一条已经在 `docs/architecture/webui-design.md` 落地），不是素材。
