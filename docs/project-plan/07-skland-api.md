## 1. 认证链路（实测打通到「拿到 cred 之前」）

当前真实链路，**每一步都实测过**：

| # | 步骤 | 请求 | 实测结果 |
| --- | --- | --- | --- |
| 1 | 取二维码 | `POST https://as.hypergryph.com/general/v1/gen_scan/login`，body `{"appCode":"4ca99fa6b56cc2ba"}` | **200**，`data.scanId` + `data.scanUrl`（`hypergryph://scan_login?scanId=…`）+ `data.enableScanAppList` |
| 2 | 轮询扫码状态 | `GET https://as.hypergryph.com/general/v1/scan_status?scanId=<id>` | **200**，`{"msg":"未扫码","status":100,"type":"A"}` |
| 3 | 换取通行证 token | `POST https://as.hypergryph.com/user/auth/v1/token_by_scan_code`，body `{"scanCode":<base64>}` | **400**，验证器报 `TokenByScanCodeReq.scanCode` 必须是 **base64** → 端点存在、字段名与类型已确认 |
| 4 | 换森空岛认证码 | `POST https://as.hypergryph.com/user/oauth2/v2/grant`，body `{"appCode":<code>,"token":<token>,"type":0}` | **401** `{"msg":"登录已过期，请重新登录","status":3,"type":"A"}`（用的是格式合法但已失效的 token） |
| 5 | 换凭据 | `POST https://zonai.skland.com/api/v1/user/auth/generate_cred_by_code`，body `{"code":<code>,"kind":1}` | 缺 `kind` → **400** `code=10001 参数错误`；字段齐全但值非法 → **500** `code=10001 服务器开小差` |

**两条必须记住的实现坑**：

1. **失败以 `status`/`code` 字段表达，不靠 HTTP 状态码**。第 4 步失败是 HTTP 401 + `status:3`；第 5 步失败是 **HTTP 500**（不是 4xx！）+ `code:10001`。**把 5xx 当「服务器故障、重试」会让客户端无限重试一个永久性错误。**
2. **`appCode` 有三个，别用错**（实测来自第 1 步响应的 `enableScanAppList`）：

   | 应用 | appCode | 来源 |
   | --- | --- | --- |
   | 明日方舟 | `7318def77669979d` | 实测 |
   | **森空岛** | **`4ca99fa6b56cc2ba`** | 实测 |
   | 明日方舟：终末地 | `dd7b852d5f1dd9da` | 实测 |
   | 官网通行证（另一条路） | `be36d44aa36bfb5b` | 读码（参考实现 `web_app_code`） |

   我们要的是**森空岛**的 `4ca99fa6b56cc2ba`。

## 2. 过时路径对照（照文档写就会踩的坑）

| 社区文档写的 | 实测结果 | 真实路径 |
| --- | --- | --- |
| `GET /general/v1/gen_scan/login` | **404 page not found** | `POST` 同路径（**GET 不存在**） |
| `GET /general/v1/gen_scan/login_status` | **404 page not found** | `GET /general/v1/scan_status` |
| `GET /general/v1/gen_scan/get_token` | 400 `scan type not support` | `POST /user/auth/v1/token_by_scan_code` |
| `POST /api/v1/user/auth/get_session` | **404 page not found** | 未找到（见下方说明） |
| `POST /api/v1/user/auth/refresh` | **404 page not found** | `GET /api/v1/auth/refresh`（**少了 `user/`**） |

**「404 page not found」= 路由不存在**（纯文本）；返回 JSON `{"code":…}` 才是路由存在。这条判据是本文件所有「存在/不存在」结论的依据。

> ⚠️ **一个把我自己骗过的假判据**：`OPTIONS` 对 `/api/v1/` 下**任意**路径都返回 200——包括 `OPTIONS /api/v1/definitely/not/a/route`。所以 **OPTIONS 不能用来判断路由是否存在**。我一开始用它得出「8 个路由都在」，那条结论已作废。

关于 `get_session`：**它在当前路径上不存在**。参考实现里也确实没有这个方法（它用的是 `auth/refresh`）。不排除它搬到别处，但**我没有找到**，标为【未找到】。

## 3. 签名机制（读码重建，**未端到端验证**）

Skland 的 `zonai.skland.com/api/v1` 接口需要签名头。算法（自 MIT 参考实现重建，**用标准库即可实现**）：

```
ts     = int(time.time()) - 1                      # 故意减 1，规避时钟偏差
hdr    = {"platform": "", "timestamp": str(ts), "dId": "", "vName": ""}
secret = f"{path}{query_or_body}{ts}{json.dumps(hdr, separators=(",", ":"))}"
sign   = md5(hmac_sha256(key=token, msg=secret).hexdigest()).hexdigest()
headers = {"cred": cred, "sign": sign, "platform": "", "timestamp": str(ts), "dId": "", "vName": ""}
```

要点：

- ⚠️ **`path` 是「完整的请求路径，含 `/api/v1`」**，例如 `/api/v1/game/player/binding`。
  **不要剥掉前缀**——这一点是本文件原先没写清、而实现里做错的地方，导致签名整体错位。
  四个参考实现都签完整路径，逐字节比对与修正见 **§14**。
- **GET 签的是原始 query 串**（`urlparse(url).query`，不含 `?`）；**POST 签的是请求体那段 JSON 文本**——即签名与**实际发出的字节**必须一致。
- `platform` / `dId` / `vName` 默认**空字符串**（不是省略）。
- `dId`（设备指纹）走 `https://fp-it.portal101.cn/deviceprofile/v4`，带一段嵌死的数据块。
  > ⚠️ **本节原先写的「参考实现里没有任何调用点传 `use_did=True`」是错的**（2026-09-29 §14 逐行复核）：
  > 三个 AstrBot 参考实现**全都无条件生成并使用一个非空 `dId`**（`Morizero` 的 `header_ca['dId'] = await _get_did()`；
  > `qihang`/`Siq5005` 把 `did` 作为必填参数）。那条结论大概来自另一条支线（`ProbiusOfficial`，已归档）。
  > **我们仍然不实现它**——生成 `dId` 需要 RSA+AES 运算（引第三方密码学库，违反零运行时依赖）
  > 且要打第三方指纹服务，与「不模拟客户端」的边界冲突。代价是**签名是否被服务端接受仍取决于它是否容忍空 `dId`**，
  > 这一点只有真实授权能证（§14.4）。

**⚠️ 未验证的部分（阶段二的第一风险）**：我**没能端到端证明这个签名是对的**。

我设计的验证实验是「用假凭据 + 正确签名访问 `player/info`，若错误码从 `10001 参数错误` 变成 `10002 用户未登录`，则签名结构正确」。**实验失败，原因不是签名错，而是设计有缺陷**：实测发现不带任何签名头时，**只要带了 `uid` 参数**，服务端就直接回 `10002 用户未登录`——也就是说**服务端在对未登录请求上根本不检查签名**，两种情况的错误码无法区分。

真正验证签名需要**一次真实授权**。这条必须留给阶段二，且阶段二第一件事就该是它。

## 4. 错误码语义（实测 + 读码一致）

| code | 含义 | 实测来源 |
| --- | --- | --- |
| `0` | 成功 | `auth/refresh` 的 200 响应 |
| `10000` | 凭据无效／未授权 | 读码（参考实现据此抛 `UnauthorizedException`） |
| `10001` | 参数错误 | `GET /game/player/info`（缺 `uid`）→ HTTP 400；`generate_cred_by_code`（坏 code）→ HTTP 500 |
| `10002` | 用户未登录 | `player/info?uid=0`、`player/binding`、`user/teenager`、`user/me`、`game/attendance` → 全部 HTTP 401 |

**HTTP 状态码与 code 无稳定对应关系**（同一个 10001 出现过 400 与 500）。**判据一律用 `code`。**

**校验顺序（实测推出）**：`player/info` 缺 `uid` → 10001；带 `uid` 但无凭据 → 10002。即**先参数、后登录**。

## 5. ⚠️ 一个反直觉的实测发现：`auth/refresh` 对无效凭据也返回成功

```
GET https://zonai.skland.com/api/v1/auth/refresh
  header: cred: junk-cred
→ 200 {"code":0,"message":"OK","data":{"token":"18a9d873337cf018b6bcd5ccbc815454"}}
```

**用一个明显无效的凭据，它返回了 `code:0` 和一个 token。** 换 App 的 UA 与我们的 UA 都是同一结果、同一个 token 值。

**含义（对本模块的设计是决定性的）**：**「刷新成功」不能当作「凭据有效」的证据。** 若阶段二拿 `auth/refresh` 做健康检查／授权状态判断，就会得到「一切正常」然后每个取数接口都回 10002——正是本项目最怕的「看起来成功但什么都没发生」。

**正确做法**：健康检查要打**真实取数接口**（例如 `GET /game/player/binding`），以 `code == 0` 为准。

## 6. 边界与合规（本项目铁律的实测支撑）

### 6.1 User-Agent 无关 → **我们不必模拟官方客户端**

我们的铁律写着「不做任何绕过、模拟客户端、反检测的行为」。社区实现全都伪造 `Skland/1.32.1 (com.hypergryph.skland; …) Okhttp/4.11.0`，所以这里必须实测。

**实测：五种 UA 结果完全一致**——空 UA、`curl/8.0`、`python-urllib/3.12`、我们自己的 UA、App 的 UA，在 `gen_scan/login` 上都返回 200 与同样的响应结构；在 `player/binding` 上都返回 401/10002；在 `auth/refresh` 上都返回同一个 token。

→ **结论：UA 不是通关门。我们用自己诚实的 UA，边界守得住。**

### 6.2 我们明确**不做**的

- **不实现 `dId` 设备指纹**（`fp-it.portal101.cn`）：它需要提交一段嵌死的指纹数据块去伪造设备身份，且参考实现里无人使用。
- **不做签到以外的任何写操作**，不模拟游戏客户端，不做反检测。
- 只用官方接口；签到是官方提供的正常操作（见 `implementation.md` §2.7 铁律第 4 条）。

### 6.3 未能确认的风险

- **频率限制**：早前调研称触顶返回 429、建议冷却 60s。**本次约 60 次探测请求未触发任何 429**，所以这条**未验证**——不能因为没触发就认为不存在。阶段二仍应按「按 uid 缓存 ≥120s + 全局冷却」设计。
- **封号风险**：官方无公开表态。**未验证**，风险自负（`02-integration-research.md` §9 R8 已记录）。

## 9. 阶段二实施记录（2026-09-29）

### 9.1 本包做完的

| 交付 | 位置 | 说明 |
| --- | --- | --- |
| 二维码编码 + PNG 输出 | `modules/skland/qr.py` | **纯标准库**（`zlib` + `struct`），字节模式，版本 1–10，四级纠错 |
| 请求层（签名 / 错误码 / 限流） | `modules/skland/api.py` | stdlib `urllib`；运输层可注入，故全部错误路径都能单测 |
| 扫码流程解析 | `modules/skland/login.py` | 纯逻辑：五步的响应解析与状态判定 |
| 装配（指令 + 定时签到） | `modules/skland/module.py` | `/ak skland [status\|login\|logout\|check\|signin]` |

### 9.2 为什么二维码是自己写的（不是选型偏好，是被逼的）

**`scanUrl` 是 `hypergryph://scan_login?scanId=…`，不是 http(s) 链接**，所以：

- 不能直接交给「按 URL 取图」的接口（那不是合法 http URL）；
- 也不能丢给在线二维码服务——那会把**登录用的 scanId 泄露给第三方**；
- 引 QR 库则与「运行时零第三方依赖」冲突。

所以自己实现。**正确性不靠自己声明**：开发期与参考实现 `qrcode` 做了**强制同掩码、含格式信息**的逐位比对，
**61 载荷 × 4 等级 × 8 掩码 = 1848 项检查，0 处不符**；PNG 侧用 Pillow 逐像素比对。
比对脚本是开发期工具、未进仓库，仓库里留的是**冻结金标**（防回归）+ 上面这次比对的结论。

比对抓到过两个真 bug，记下来给后来的人：

1. **格式信息那 15 位的接线写成了转置**（行/列 8 弄反）——矩阵看起来「大体像」，
   只有格式位错，扫码器直接读不出纠错等级。
2. **PNG 灰度极性写反**：1 位灰度里采样值 `1` 是**白**、`0` 是**黑**，
   按直觉「深色 = 1」写会得到**整张反色**的图。

### 9.3 新增的两条实测/设计约束

- **限流冷却必须按端点记，不能全局。** 扫码授权是**连着三步**的顺序调用，
  全局冷却会把它们互相卡死——这是个会让登录永远失败的 bug，被单测抓出来。
- **签名测试锁的是字节序，不是服务端认可。** `sign_headers` 有金标（`path + query/body + ts + json(hdr)` 的
  拼接顺序），但那**只能证明拼接没变**；服务端认不认它，只有一次真实授权能证——
  这正是 `/ak skland check` 的意义：签名错了会回 10001/10000 而不是 10002。

### 9.4 本包**刻意没做**的（以及为什么）

**干员疲劳 / 基建状态 / 干员查询一律未实现。**

理由不是时间不够，而是**这几条路由连存在性都没实测过**——§1 的五步链路是逐条打过的，
而基建/干员那几条没有任何请求记录。照文档猜路径正是本项目栽过的坑
（`FormData` 那条「照文档抄的 API 事实」在真实环境里根本递不过去）。
**宁可少做一个功能，也不要照文档写一个跑不通的。**

`api.sign_in()` 与 `api.player_info()` 是**唯二有实测记录**的业务端点（无凭据时分别返回
401/10002、缺 `uid` 时返回 10001），所以它们实现了，但成功响应体的字段名在代码里标了
`UNVERIFIED`，并且按**多个候选键**读取、取不到就抛——**不返回空值假装成功**。

### 9.6 服务端同码不同义，必须靠 message 区分

`code=10001` **不是只有一种含义**：

| 场景 | 码 | 判据 |
| --- | --- | --- |
| 请求缺必填参数 | 10001 | message 说参数错误 |
| **今天已经签过** | **也是 10001** | message 含「已签到 / 重复签到」 |

出处：`Morizero1125/skland_auth.py:215-216` 的注释（MIT）。**不区分它，用户签过一次
之后每次都会看到「参数错误」，然后去查一个并不存在的 bug**——这正是 `_do_signin`
上一版的真实行为。判据只认服务端自己的措辞，判不出来就按真错误处理
（**宁可报错，不假装成功**）。

## 10. 「二维码发不出去」的排查结论（2026-09-29）

**结论：图片段确实发出去了，那条「已确证的失败」是探针的打印盲区造成的误判。**

### 10.1 证据链

| 环节 | 结论 | 证据 |
| --- | --- | --- |
| AstrBot 侧是否支持 `Image` | **支持** | `aiocqhttp_message_event.py:38` → `convert_to_base64()` → `{"type": "image", "data": {"file": "base64://…"}}`；`send_message`（:127）走 `_parse_onebot_json`（:79） |
| 换成本地文件路径会不会绕过 | **不会** | 同一处对 `Image` **一律**转 base64，**换形态无用**（`File` 才走 `as_uri()` 分支） |
| 我们的 payload 里有没有图片段 | **有** | 探针原始输出：`[SEGMENTS] ['text', 'image']`，`message` 数组含 `{"type": "image", "data": {"file": "base64://iVBORw0KGgo…"}}` |
| 生成的 PNG 是否合法 | **合法** | 签名 `89 50 4E 47`、chunks `IHDR/IDAT/IEND`、`328x328 depth=1 colour_type=0 interlace=0`、base64 往返逐字节一致 |
| 发送是否失败 | **没有失败日志** | 唯一异常是探针断开后轮询结束时的回执（`skland.module:575`），与二维码那一步无关 |

### 10.2 误判是怎么产生的（值得记的教训）

`/tmp/onebot_probe.py` 的 `_extract_text()`（:64）**只提取 `type == "text"` 的段**，而打印语句（:117）用的正是它的返回值——**`message` 数组里的图片段被整个丢掉了**。

于是「测试通道只看到 text」被读成了「没有发图片」，而真实情况是**探针看不见图片**。

**教训**：**观测工具的盲区会被误当成被测对象的事实。** 排查「某个东西没出现」之前，先确认**观测者能看见它**——这与本项目此前几次「静默匹配不上」是同一类问题，只是这次盲区长在测试脚手架里。已给探针加了 `[SEGMENTS]` 与 `[RAW]` 两行输出（保留原打印）。

### 10.3 真机上「没收到」的最可能原因与对策

**服务器侧一切正常**，所以问题在**呈现**：328×328 的 1:1 方图，**QQ 默认渲染成缩略图，需点开才见全图**。用户看到「一条带字的气泡 + 一张小图」，容易当成装饰滑过去。

对策（已实施）：

1. **倍率 8 → 12**（328 → 492px）。代价可忽略：PNG 439B → 576B，base64 588 → 768 字符。
2. **提示语写明「如果图太小，点开图片看大图」**。
3. **成功也留一行 INFO**（字节数 + 段数）。此前只有失败有日志，**成功时反而无声**，于是无法区分「发了但没看见」与「根本没发出去」——这正是本次误判能存活的原因。

> **边界**：以上三条**都只在服务器侧验证过**（payload 与 PNG 是实测的），**真机呈现未经证实**——本包无真机。若真机仍看不到图，下一步应查 **NapCat 侧的 `base64://` 处理**（那是我们观测不到的一层），而不是继续改 AstrBot 侧。

## 11. 授权失败的可诊断性（2026-09-29，线上失败促成）

### 11.1 现场

用户扫码后收到：

```
授权流程失败（没有拿到凭据）：响应里没有 data 对象：字段有 msg
```

而**服务端日志里什么都没有**——只有更早的「已发送二维码（686 字节，2 个消息段）」。
**判据是对的**（缺 `data` 确实算失败），**缺的是定位**：不知道哪一步、也不知道服务端回了什么。

### 11.2 `scanCode` 来源的核实结论（任务点名要查的疑点）

**结论：取值来源与编码方式都是对的，线上那次失败不在这一层。**

| 疑点 | 结论 | 依据 |
| --- | --- | --- |
| scanCode 来自哪里 | 第 2 步**轮询响应**的 `data.scanCode`，**不是** `scanUrl` 里的 | ① 本文件 §1 第 2 步的实测形态；② MIT 参考实现 `morizero_main.py:530`：`scan_code = (res.get('data') or {}).get('scanCode')` |
| 是否要再编码一次 | **不要**。原样透传 | §1 第 3 步实测：验证器要求 `scanCode` **必须是 base64**。再编码一次会变成"对 base64 再做 base64" |
| 非 base64 时怎么办 | 本地先拦住并说清楚 | `decode_scan_code` 校验后抛「扫到的 scanCode 不是合法 base64（含长度与摘要，不含值）」 |

**因此**：如果失败在第 3 步，说明**服务端拒收了一个格式合法的 scanCode**（已用过／已过期／与 scanId 不匹配），而不是我们取错了字段或编错了码。**这一条以前无法区分，现在可以了。**

### 11.3 轮询状态语义的一处修正（顺带查出的真 bug）

对照 MIT 参考实现 `morizero_main.py:512-528`，`status` 的语义比我们原先掌握的更完整：

| `status` | 含义 | 我们原先的处理 | 当时改成 |
| --- | --- | --- | --- |
| `100` | 未扫码（实测值） | WAITING ✓ | WAITING ✓ |
| `0` + 有 `scanCode` | 已扫码 | SCANNED ✓ | SCANNED ✓ |
| `0` + **无** `scanCode` | 已扫码、等手机确认（**参考实现的说法**） | ❌ 误判为 FAILED | WAITING（提示"已扫码，等待手机确认"） |
| `102` | 二维码已失效（**参考实现的说法**） | ❌ 误判为 FAILED（只能靠 msg 猜） | EXPIRED（回执直接说"已失效，重发一次"） |

> ⚠️ **本节后来被实测推翻了一部分，见 §12。** 这张表**把参考实现的 `0` 当成"已扫待确认"**，
> 而真实服务端用的是 **`101`**——于是**真实的等待态仍然无人认领**，落进了"未知 → FAILED"
> 那一支，**轮询当场中止**，用户点确认时已经没人在等（§12.1 是现场）。
> 教训：**参考实现的状态码不是本服务器的事实**，两处都要标注来源。

### 11.4 现在的失败长什么样

日志与回执**是同一段文案**（用户把回执发回来，就等于给了我们日志里那一行）：

```
第 3 步（用 scanCode 换取通行证 token）失败：响应里没有 data 对象
｜服务端：HTTP 200；msg='scanCode 无效'；没有 data 字段
```

每个字段都有出处：**第几步**来自 `login.Step`；**HTTP 状态**由 `call_unauthenticated_detailed` 带回（此前被 `_call` 丢掉了）；**服务端字段**由 `login.describe_response` 渲染。

另外**每次轮询的状态变化也记一行**（`扫码状态变化：waiting|HTTP 200；status=100；…`）——线上那次的日志只有「已发送二维码」一行，**中间发生过什么完全没痕迹**，于是无从判断用户到底扫没扫。

### 11.5 凭据脱敏的规则（硬红线）

`scanCode` / `token` / `cred` / **授权 `code`**（即 `data.code`，能换 cred 的那个），以及 `scanId` / `scanUrl`（登录票据，拿到即可顶替用户走完链路）——**一律不落原文**，只输出 `<已隐去 len=N sha256=前8位>`。

三条附加规则：

1. **顶层 `code` 例外**：那是**状态码**（判据就是它），必须记录。授权 `code` 只在 `data.code` 下，**靠位置区分**。
2. **`data` 里非凭据键连值都不打印**，只给类型与长度（`str len=5` / `列表 len=2` / `对象{...}`）——形状信息足够判断"字段名猜错了"，而值可能带个人数据。
3. **服务端消息过一道 `scrub`**：抹掉 16 字符以上的 token 形状串。第 3 步的验证器报错**可能回显我们发去的 scanCode**，这一道是兜底。

**护栏可证伪**（已实测）：把 `redact_marker` 换成直接渲染原值，**7 条测试立刻变红**，还原后逐字节一致、全绿。

### 11.6 闭环缺口

- **未发起真实扫码复现**（任务要求不擅自消耗用户的二维码）。这次的产出是**把定位能力装上**，不是"修好了那一次失败"。
- 那次的成因因此**仍未定论**。最可能是**第 3 步拒收了一个格式合法的 scanCode**（用户在 11:40 / 11:42 连续发过两次 `login`，也可能扫到了较早那张码的会话）。**下次再失败，日志会直接给出答案**——这正是本包的目的。
- 若下次看到 `第 3 步 … msg='…'`，优先怀疑**码被用过或过期**；若看到 `第 5 步 … code=10001`，那才是我们请求体的问题（`kind` 缺失之类），与 scanCode 无关。

## 12. 「已扫码待确认」被误判成失败（2026-09-29 第二次线上失败）

### 12.1 现场（用户原话：**「扫的瞬间发送这句话，我手机授权同意后无事发生」**）

```
授权没走完。第 2 步（轮询扫码状态） 失败：已扫码待确认
｜服务端：HTTP 200；status=101；type='A'；msg='已扫码待确认'；没有 data 字段
```

**这条报错准确得刺眼**——它把「已扫码待确认」当成失败原因说了出来。真正的缺陷不在措辞，
而在**判定**：`101` 是我们**从没实测过**的取值，于是落进「未知状态 → `FAILED`」那一支，
**轮询当场 `return`**。用户随后在手机上点确认时，**已经没有任何人在等那个结果了**。

> 因果要连起来看：上一包（§11）刚把诊断能力装上，这一包就靠它一次定位。**没有 §11，这条
> 报错只会是"授权流程失败"四个字。**

### 12.2 `status` 语义全表（**逐值标注证据来源**）

| `status` | 含义 | 处理 | **证据来源** |
| --- | --- | --- | --- |
| `100` | 未扫码 | WAITING（继续等） | **实测**（阶段一） |
| **`101`** | **已扫码、等手机确认** | **AWAITING_CONFIRMATION（继续等）** | **实测**（本次现场） |
| `102` | 二维码已失效 | EXPIRED（终态，提示重发） | 参考实现，**`UNVERIFIED`** |
| `0` | —— | 落入默认分支（继续等），**不给特殊含义** | 参考实现；且 `0` 是本协议的**通用成功码**（第 1 步的成功响应就是它） |
| 消息含「过期/失效/expired」 | 终态 | EXPIRED（终态） | **实测**（服务端自己写的措辞） |
| 其它任何值 | 未知 | **WAITING（继续等）** | —— |
| 出现 `scanCode` | 已扫码 | SCANNED | **实测**（结构判据，与 `status` 取值无关） |

**用户确认之后 `status` 变成什么——我们没有实测数据，标【推测】。**
最可能是**同一个 `status` 下直接带上 `data.scanCode`**（参考实现的取值域里也没有第二个"成功"值）。
**但这不影响正确性**：成功判据是**结构**（有没有 `scanCode`），不是数字，所以无论它变成
`0` / `101` / 别的什么，只要带上 `scanCode` 就会被认出来。这正是"不猜数字"的价值。

### 12.3 改成了什么

1. **默认分支倒过来**：从「认识的值继续等、不认识的值报失败」改成
   **「没拿到终态信号就继续等」**。`FAILED` 这个状态被**删掉**了——没有任何**实测证据**
   支持某个 `status` 是"轮询终态失败"，留着它只会再制造一次同类误判。
2. **超时兜底分两种说法**：一直没扫到 → 「二维码超时了」；**扫到了却始终没确认** →
   「扫到了，但一直没在手机上点确认」。后者才是他真正需要知道的事（他以为自己已经做完了）。
3. **扫到之后延长等待窗口**（`CONFIRMATION_GRACE_ATTEMPTS`，30 次 × 2s = 再给 60 秒）：
   `POLL_ATTEMPTS` 对应的本来是**二维码有效期**，可**一旦扫到，有效期就不再是约束**——
   若用户在第 110 秒才扫到，原窗口只剩 10 秒，他还没点完我们就超时了。
4. **扫到时主动说一句**「已经扫到码了，请在手机上点确认」（只说一次，不刷屏）。

**成功判据一个字都没放宽**：仍然只认 `scanCode`；`data` 缺失该报错还是报错（§11 那条断言照旧）。

### 12.4 这次的可证伪验证（做过两次，第二次才发现缺口）

把缺陷**注入回去**，确认新护栏**真的会红**：

| 注入 | 结果 |
| --- | --- |
| A. 默认分支改回「终态」（未知值结束轮询） | ✅ 红（**但第一次跑时是绿的——见下**） |
| B. 删掉实测的 `status == 101` 分支 | ✅ 红 |

> **A 第一次是绿的，这条值得记。** 当时钉「继续等」的那条测试用的是实测的 `101`，
> 而 `101` 走的是**它自己那条分支**——**默认分支（未知值）根本没被走到**。
> 也就是说：**我以为钉住了"未知值不判死"，其实只钉住了"101 不判死"**。
> 补了一条**端到端注入 `status=7`** 的用例之后 A 才变红。
> 教训：**注入实验要注入到"我以为被测到、其实没被走到"的那条路径上**——只验一次通过，
> 很容易恰好验在解释器会走的另一支上。

改动落在 `modules/skland/login.py`（判定）与 `modules/skland/module.py`（轮询循环与措辞）。

### 12.5 下次真机复查要看什么

1. **扫到码时**：回执应当是「已经扫到码了，请在手机上点确认」，**不是**任何失败字样；
   日志里应出现一行 `扫码状态变化：awaiting_confirmation|…status=101…`。
2. **点确认后**：应当走完并回「授权成功」。若它变成了别的 `status` 而**带上了 `scanCode`**，
   流程同样会成功——**请把那行日志留给我**，我们就能把"确认后是什么值"补进 §12.2。
3. 若**扫到但一直没确认**：超时说法应当是「扫到了，但一直没在手机上点确认」。
4. 若**始终看不到图/扫不了**：那是 NapCat 侧的事（§10.3 的边界），不要回来改 AstrBot 侧。

## 13. 第 3 步失败的真因：`Content-Type` 缺失（2026-09-29 第三次线上失败）

### 13.1 现场

```
[12:02:18.294] 扫码状态变化：scanned|HTTP 200；status=0；type='A'；msg='OK'；
               data{scanCode=<已隐去 len=120 sha256=8953e071>}
[12:02:18.465] 第 3 步（用 scanCode 换取通行证 token） 失败：响应里没有 data 对象
               ｜服务端：HTTP 400；msg='Key: '<已隐去 len=18>.scanCode' Error:Field
                 validation for 'scanCode' failed on the 'required' tag'；没有 data 字段
```

用户强调：**两次都是在「手机点授权的瞬间」发出的**——不是超时问题。

### 13.2 根因（实测，不是推断）

**我们的未签名 POST 没有声明 `Content-Type`。**

`urllib` 在「带 body 却没有显式 `Content-Type`」时会**替我们补** `application/x-www-form-urlencoded`。
服务端于是按**表单**绑定，body 里明明是正确 JSON 也一个字段都读不到 → `scanCode` 为空 →
`required` 校验失败。**字段名对、值却是空的**——这句话的全部含义就在这里。

实测证据（`tmp/s6_probe_content_type.py`，起本地 HTTP 服务抓真实请求头）：

```
A. 未签名路径实际发出的：Content-Type: application/x-www-form-urlencoded
B. 显式设成 JSON 之后：  Content-Type: application/json
（两种情况下 body 都是正确的 JSON 文本）
```

**为什么只有第 3 步出事**：`Content-Type` 原先只设在**签名分支**里，而第 3 步是**未签名**调用。
第 1、2 步要么是 GET、要么不带 body，所以从未暴露。**两条路径的这次漂移就是本缺陷的成因**——
和 §11.3「参考实现的状态码被当成事实」同源：**同一件事在两处实现，迟早会分叉。**

### 13.3 那个 `<已隐去 len=18>` 是什么

它是**服务端自己的结构名** `token_by_scan_code`（18 字符），被 `login.scrub` 的
「长串一律隐去」规则（`[A-Za-z0-9+/=_\-]{16,}`）遮掉了。

**遮得比必要的多，但方向是安全的**，所以不去调窄这条规则——把阈值调低会让真凭据漏出来，
调高则可能放过服务端回显的 `scanCode`。**宁可多遮**。

### 13.4 改了什么

1. **`Content-Type` 由「有没有 body / 是否签名」共同决定**，一处实现：

   ```python
   if payload_bytes is not None or signed:
       headers["Content-Type"] = "application/json"
   ```

   两个条件都**不能省**：① 带 body 的必须声明（本缺陷）；② 签名请求（含**不带 body 的
   POST**，例如签到）一贯声明 JSON，改它属于顺手改行为。签名分支里原先那行**删掉了**，
   免得两条路径再次分叉。
2. **新增请求侧的形状诊断**（`api.describe_request_shape`）：
   **只有键名、类型与长度，绝无任何值**。失败文案随之多一段
   `｜我方请求：Content-Type=…；请求体={scanCode=str(len=120)}`。
   - 为什么需要：只有响应摘要时，「服务端说某字段是空的」有**两种相反的解释**——
     我们没发，或者发了但对方没按 JSON 读。形状能当场分开。
   - `Content-Type` **缺失**时**明说缺失**，并点出 `urllib` 会补什么。那个自动补的默认值
     正是本事故的成因，写成一句无声的「未设置」等于把线索藏起来。
3. `RawCall` 增加 `request_shape`，`RawResult` 承载 `_call_raw` 的三元结果。

**成功判据与各种校验一个字都没放宽。**

### 13.5 可证伪验证（两轮注入，还原逐字节一致）

| 注入 | 结果 |
| --- | --- |
| A. 把 `Content-Type` 改回只在签名分支设置（复现本 bug） | ✅ 3 条红（含**端到端**那条） |
| B. 让形状描述器渲染真值（复现泄露） | ✅ 2 条红（凭据不外泄当场抓住） |

`restored byte-for-byte: True`。脚本在仓库外（`tmp/s6_falsify.py`）。

**端到端那条是本包最有价值的护栏**：假传输被写成「只认 `Content-Type: application/json`」
（即把线上服务端的真实行为编码下来），于是**本缺陷一旦回来，本地就会红**——而它此前
在真机上坏了一整晚、本地 826 条测试全绿。

### 13.6 教训（与前两次同族）

这条缺陷的形状是「**本地全绿、真机必挂**」，而它之所以能活下来，是因为**没有任何测试
把"服务端怎么解析我们的请求"这一层编码下来**。补上它之后，同一类问题不再需要真机才能发现。

另外值得记一条**排查方向**：`required` 校验失败**不等于**"我们没发这个字段"。
它只说明**服务端认为它是空的**——两者之间隔着传输层。这次的形状诊断就是把这一层照亮的东西。

### 13.7 下次真机复查要看什么

## 14. 签名修正：`path` 曾被剥掉 `/api/v1` 前缀（2026-09-29 第四次线上失败）

### 14.1 现场

第 3 步的 `Content-Type` 修好之后，**登录链路五步全过、凭据落盘**，但紧接着的「连接验证」失败：

```
[12:10:46.878] 授权成功，凭据已落盘（不打印内容）
[12:10:47.159] [WARN] 凭据已失效，已清除本地凭据
连接验证：凭据无效，需要重新授权（HTTP 401，code=10000）
```

`code=10000` 是「凭据无效」——**这个错误码把方向引偏了**：它长得像"凭据坏了"，
而签名不对也会落到同一档。上一包刚验证过签名「从未端到端验过」，所以这次直接去比对签名算法。

### 14.2 逐项比对：我们的实现 vs 各参考实现

### 14.3 结论：**我们错了**，错在「取值」而不是「算法」

`sign_headers` 本身**一直是对的**——拼接顺序、JSON 形态、键顺序、算法、GET/POST 取值全部与

1. **签名是否被服务端接受**——**本包依旧无法端到端验证**。服务端对未登录请求不校验签名
   （§3），所以没有真实凭据就无法区分。**必须再扫一次码**（由总监安排）。
2. **`dId` 是否被要求非空**——**这是本包之后最大的未知**。
   - 有利于"空也行"的证据：`platform` / `vName` 在 Morizero（一个在用的实现）里就是空串。
   - 服务器**必须从我们发出的头部重建被签名的 JSON**（否则它无法知道客户端自选的 `dId`），
     所以**自洽的空 `dId` 在签名层面是成立的**——除非服务端额外校验它非空/合法。
   - **不改的理由**：生成 `dId` 需要 RSA+AES（要引第三方密码学库，违反零运行时依赖）
     且要打 `fp-it.portal101.cn`（与"不模拟客户端"的边界冲突）。**这是所有者级别的取舍，不该由本包单方面翻案。**
3. **`ts` 偏移 `-1` vs `-2`**：未验证。**但时钟偏差这条已被排除**——
   实测容器时间与外部参考只差 **+0.0s**（宿主 +0.3s），所以 `-1`/`-2` 都在任何合理窗口内。
   保持 `-1` 不动（最小改动；两者都无法证明更优）。

### 14.6 教训

**错误码把方向引偏了。** `code=10000`（凭据无效）同时覆盖「凭据坏了」与「签名不对」两种情况，
而当时刚拿到新凭据，**最自然的解释是"凭据出问题"**——于是会去查凭据链路，而真因在签名。

**能打破这个僵局的只有一条：拿纯函数做逐字节比对。** 签名不依赖网络、不依赖凭据，
只要把「参考实现在同样输入下算什么」摆出来，实现里的偏差立刻现形——
**这是本包唯一真正解决问题的动作**，比读代码、比看错误码都直接。

**另一条**：这一族缺陷（§11 状态码、§12 未知状态、§13 `Content-Type`、§14 路径前缀）有个共同形状——
**"我们以为的事实"与"参考实现/服务端的事实"不一致，而本地测试只钉住了前者**。
§13 与 §14 的护栏都补上了「把对方的真实行为编码进测试」这一层（一个用假传输只认 JSON，
一个用逐字节重算钉住签名输入）。**能本地钉住的，就别留给真机。**

## 15. 绑定信息是**三层**结构，我们每一层都少找了一格（2026-09-29 第五次线上失败）

### 15.1 现场：认证已经通了，坏的是形状假设

签名修正（§14）之后，登录链路与认证**全部走通**——报错不再是 `10000`/401，而是：

```
连接验证：连接失败：绑定信息里没有 uid（响应结构与预期不符）
```

**这条报错本身是有信息量的**：能拿到业务数据说明**认证通过了**（否则服务端只会回
`10000`/`10002`）。所以坏的不是凭据、也不是签名，而是**我们对响应形状的假设**。

### 15.2 真实结构（**四条参考实现一致**，逐条给出处）

```
data.list[]              每个元素是一个 app
  appCode                "arknights" / "endfield" …
  defaultUid             该 app 的默认角色（可能缺）
  bindingList[]          该 app 下的角色
    uid                  ← 角色 uid 在这里
```

| 参考实现 | 许可 | 出处 | 取法 |
| --- | --- | --- | --- |
| `Morizero1125/astrbot_plugin_arknights_skland` | **MIT** | `main.py:209-213` | `binding['list']` 里筛 `appCode == 'arknights'` → `arknights['bindingList']` → `b['uid']` |
| 同上 | — | `main.py:160-163` | `uid_dict[app['appCode']] = app['defaultUid']`，缺则 `app['bindingList'][0]['uid']` |
| `Siq5005/astrbot_plugin_arknights` | **MIT** | `core_skland.py:697-707` | `(data.get("data") or {}).get("list")` → `app.get("bindingList")` → `item.get("uid")` |
| `qihang518887/astrbot_plugin_sklandv2` | （本文件 §7 已复核） | `skland_api.py:405-427` | `response["data"]["list"]` → `item["bindingList"]` → `binding.get("uid")` |
| `Azincc/astrbot_plugin_skland` | **无 LICENSE**，仅作旁证 | `skland_api.py:432-443` | 与上同形 |

**四/四都用 `list[].bindingList[].uid`；`defaultUid` 只有 Morizero 用（1/4，作兜底）。**

### 15.3 我们错在哪：三个候选路径**各少一层**

原实现（`api.binding_uid`）依次试过三个位置，**每一个都不完整**：

| 试过的路径 | 真实位置 | 差在哪 |
| --- | --- | --- |
| `data.uid` | `data.list[].bindingList[].uid` | 少了 `list[]` **和** `bindingList[]` |
| `data.bindingList[].uid` | 同上 | 少了 `list[]` |
| `data.list[].uid` | 同上 | 少了 `bindingList[]` |

**更要紧的是**：测试 `test_binding_uid_reads_flat_and_nested_shapes` 把这三个**猜出来的**
形状钉进了护栏，于是本地 841 条全绿、真机一个都不中。这与 §14 的
「本地测试只钉住了我们自己的假设」是**同一个病**，只是这次错的不是取值而是**层级**。

### 15.4 改成了什么

1. **解析抽成纯函数** `arknights_uid(payload)` / `binding_app_codes(payload)`：不碰网络，
   可以脱离传输层单测；`binding_uid()` 只负责发请求 + 组织错误文案。
2. **按 `appCode == "arknights"` 过滤**：一个森空岛账号可同时绑多个游戏，取错了会拿
   终末地的 uid 去查方舟，而服务端只会回一个含糊的参数错误。
3. **`defaultUid` 优先、`bindingList[].uid` 兜底**（与 Morizero 同序）。
4. **删掉三个没有证据的候选路径**——留着它们等于让错误的结构假设继续传播。
5. **失败文案带上"看到的应用"与响应结构**（见 §15.5）：
   ```
   绑定信息里没有明日方舟的 uid（看到的应用：endfield）｜响应结构：{code=int、data={list=列表[…}}}
   ```
   这一句把两种失败分开了：**"结构没认出来"** 与 **"认出来了，但这个账号没绑方舟"**——
   原先一律说「没有 uid」，用户只能再扫一次码去试。
6. **替换**（不是扩充）那条钉住错误形状的测试，真实形状另起一条；
   两处假传输的 fixture 也一并改成三层结构。
7. **附带修正一处口径不实**：`module._do_check` 的成功回执原先写着「已脱敏显示长度」，
   **实际打的是完整 uid**。现在打码成 `11******67`（首尾各留两位），并把措辞改成
   `共 N 位`。理由：**uid 不是凭据**（泄露它顶替不了任何操作，签名与 `cred` 才是），
   但它是**个人标识**，而回执可能出现在群聊里（群里只有管理员能触发，可回执全群可见）。

### 15.5 新能力：形状诊断（`api.describe_structure`）

只有响应摘要时，「服务端说某字段是空的/没有」有**两种相反解释**——字段真不在，
或者**在别处**。这一层以前完全看不见，所以每次都得再扫一次码去试。现在失败时带上形状：

```
{code=int、data={list=列表[{appCode=str(len=8)、bindingList=列表[{uid=str(len=13)}]} |
  {appCode=str(len=9)、bindingList=列表[{channelMasterId=str(len=1)、nickName=str(len=2)、
   uid=str(len=10)} | {nickName=str(len=4)、uid=str(len=10)}]、defaultUid=str(len=10)}]}}
```

设计要点（每条都有理由，不是风格偏好）：

- **"永不渲染值"而不是"按凭据键名脱敏"**：前者**结构上不可能泄露**。响应里没有 token，
  但有 `uid` / `nickName` 这类个人数据，而「哪些键算敏感」会随接口变——不渲染值就不必跟着变。
- **列表项不额外消耗一层深度**：列表只是同类元素的容器，让它算一层会让「数组套对象」
  凭空多一层，而这一层预算恰恰要留给 `bindingList[]` 里面的字段（`uid` 就在那儿）。
  第一版就是栽在这里——形状停在第 2 层，**诊断本身看不见问题**。
- **超出展示上限要报总项数**（`共 N 项`），静默截断会让人以为看全了。
- 长度上限 480 字符且**截断时明说**（它会同时进日志与 QQ 回执，本项目约定二者同文案）。

### 15.6 可证伪验证（注入 → 红 → 逐字节还原）

注入：让 `arknights_uid` **不再往下钻 `bindingList`**（即复现"少一层"这个缺陷本身）。

```
original sha256 : f96ef853a5575ea92059cfca3f45ee4bc0d31e97b4245448afb1de1ddba1efc7
1. guard on the FIXED tree    -> 35 passed                       exit=0
3. guard on the BROKEN tree   -> 3 failed, 32 passed             exit=1   <- 红
4. restored                   -> identical: True
5. guard green again          -> 35 passed                       exit=0
GUARD IS FALSIFIABLE AND REAL: True
```

**做这个实验时我自己踩了一个坑，记下来给后来的人**：第一版脚本用
`pathlib.write_text()` 还原，而它在 Windows 上会把 `\n` 翻译成 `\r\n`——
于是"逐字节还原"**实际把整个文件的行尾改掉了**（sha256 对不上，才发现）。
改成**全程字节操作**（`read_bytes` / `write_bytes`）后还原才真正一致。
本项目先前已经因为"用 shell 重写文本"损坏过一个文件，这是同一族问题的另一副面孔。

### 15.7 顺手核查：同一模块里其它解析有没有同类问题

| 解析点 | 有没有猜字段 | 结论 |
| --- | --- | --- |
| `binding_uid`（本包修正） | **有**，三处各少一层 | 已按四条参考实现改正，并加形状诊断 |
| `sign_in` / `_do_signin` | **没有** | 只判 `code==0`（由请求层保证）+ `data` 非空；判据不足时回执**明说**「结构未验证，已如实记录」——**没有任何字段名假设** |
| `player_info` | **没有** | 纯透传，**刻意不解析任何字段**（照文档猜字段名正是本项目栽过的坑） |

> 顺带记一条**不属于本包范围**的观察：`player_info` 目前**只有测试在用**，
> 模块侧还没有调用点（干员/基建那几条路由被刻意推迟到实测之后）。
> 要不要保留这个"已实测存在、但暂未使用"的方法，属所有者取舍，本包不擅自删。

### 15.8 下次真机复查要看什么

1. `/ak skland check` 应当回 **「连接正常（绑定 uid=11\*\*\*\*\*\*67，共 10 位）」**——
   那说明**绑定解析对了**，同时也就是**签名被服务端接受的最终证据**（§14.4 的未验证项）。
2. **若仍失败**：回执现在自带「看到的应用」与「响应结构」，**把那整句发回**即可定位——
   `看到的应用：` 里没有 `arknights` 就不是结构问题，而是**这个账号没绑方舟**。
3. 一旦通了，签到（`/ak skland signin`）就是下一个要亲眼看的动作：
   它的**请求方法与成功响应体仍未验证**（§9.5），失败会如实抛出，不会静默当成功。


## 16. 签到 `10001` + 指令异常冒到宿主（2026-09-29 第六次线上失败）

### 16.1 现场

```
/ak skland signin
→ module.py:368 handle_command / :299 _do_signin / api.py:699 sign_in
  SklandParamError: 接口参数错误（不会重试）（HTTP 400，code=10001）
```

并且异常**冒到了宿主**：

```
[Core] [ERRO] [method.star_request:57]: Star ...main_ak handle error: 接口参数错误…
在调用插件 astrbot_plugin_arknights_toolbox 的处理函数 ak 时出现异常
```

### 16.2 真因一：签到**必须带 `gameId` 与 `uid`**

我们发的是**空 body**，服务端回 `10001`（参数错误）。三个参考实现**完全一致**：

| 参考实现 | 位置 | 请求形态 |
| --- | --- | --- |
| Morizero1125（**MIT**） | `skland_auth.py:212-219` | `POST` + `{'gameId': game_id, 'uid': uid}`（`game_id` 默认 **1**） |
| Siq5005（**MIT**） | `core_skland.py:752-757` | `POST` + `{"gameId": binding.game_id, "uid": binding.uid}` |
| qihang518887 | `skland_api.py:434-443` | `POST` + `{"gameId": binding.game_id, "uid": binding.uid}` |

**含义**：签到是**账号级**操作，服务端必须知道给谁签、签哪个游戏。`uid` 取自
`binding_uid()`（§15 修好的那三层结构解析）。

**成功响应体**（参考实现读法，仍标 `UNVERIFIED`）：`data.awards[]`，每项

### 16.3 真因二：`10001` 有两种含义（见 §9.6）

Morizero1125 的注释原文：「重复签到返回 `code=10001`（message 含「重复签到」），
与凭证失效同码，需先按 message 识别」。**不区分它，用户签过一次之后每次都会看到
「参数错误」**——然后去查一个并不存在的 bug。

### 16.4 真因三（与森空岛无关，是通病）：指令异常冒到宿主

`handle_command` **没有外层兜底**，任何未捕获异常都会变成宿主的一段栈 + 一句
「出现异常」——**用户看不懂、我们还丢掉了「是这条指令出的错」这个上下文**。

修法：`handle_command` 把分发逻辑包进 `try/except`，**记 ERROR 日志**（含栈）并回一句
带原因的话。**绝不吞掉**（本项目铁律：失败要显式）——只是不往宿主扔。

**为什么只改 skland、不抽到 `core/`**：`shift_reminder` 的命令处理路径已经自己兜住了
各类领域错误，它的失败面（写配置、cron）与这里不同；把兜底抽成共享机制属于**动核心**，
须单独裁决。本模块先自己兜住，边界写进代码注释。

### 16.6 教训

**这是第六次「我们对某个外部事实的假设是错的」**（前五次：图片段、状态 101、请求体
层级、`Content-Type`、签名前缀、绑定层级）。而**每一次的错误码都指不到真因**：
`10000` 说「凭据无效」而凭据是好的；`10001` 说「参数错误」而真相是缺两个必填字段。
**唯一可靠的定位手段是实测**——抓真实请求、看真实响应、逐项对参考实现的确切代码。

### 16.7 下次真机复查要看什么
