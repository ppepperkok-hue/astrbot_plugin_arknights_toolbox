# MAA 远程触发 · 环境与能力边界评估

> **本包定位**：把立项阶段对 MAA 的**推测**变成**事实**。用户要求「搞清楚环境和用户需求」。
> **红线遵守**：MAA 是 **AGPL-3.0**，本项目是 MIT。本文**没有复制任何 MAA 代码或资源文件**；引用仅为极短的配置键名与协议字段名（事实性标识符），用于说明能力边界。所有 MAA 侧观察均在**只读**前提下进行。
> **证据强度标注**：**【实测】**＝本机/本服务器实际观察；**【官方文档】**＝MAA 官方文档站或官方仓库；**【社区】**＝第三方实现或社区文章；**【推测】**＝推断，未验证。

## 0. 一句话结论

**能力是真的，网络比立项时假设的简单得多，而且不需要用户额外装任何东西；但"该不该做"卡在一个还没答案的需求问题上——而这个问题从立项问到现在，一直没人回答。**

具体说：

- 触发能力 **【实测 + 官方文档】**：MAA 官方有**远程控制协议**，且**用户已装的 6.18.0 就支持**（配置键齐全）。**不需要升级、不需要额外软件。**
- 网络路径 **【实测】**：立项时担心的"链路最长（服务器→手机→本机）"**是错的**——协议的方向是 **MAA 主动出站轮询我们的服务器**，因此**不需要内网穿透、不需要反向连接、不需要开本机端口**。服务器本来就公网可达，**零额外组件**。
- 能力边界 **【官方文档 + 既有调研】**：**只能触发"跑一次已配好的基建任务"，带不了班次参数**。也就是说**能"让它现在跑"，不能"让它跑第 2 班"**。
- 真正的拦路虎 **【实测】**：**用户的 MAA 已经在用两个定时器（04:00 / 23:00）跑基建**，而且**排班表就是从 riic.autos 导出的三班表**。所以「到点自动换班」这件事**在他机器上早已具备条件**——**我们必须先问清楚：加这一层，补的是哪个缺口？**

## 1. A · MAA 有没有"被远程触发"的正规能力

### 1.1 有，而且是官方协议，方向与我们原来的假设相反

**【官方文档】** MAA 文件站有一份独立的[「远程控制协议」](https://docs.maa.plus/zh-tw/protocol/remote-control-schema.html)（简体版同址 `/zh-cn/`）。其原文关键句：

> 「若要實作對 MAA 的遠端控制，您須提供一個服務，該服務必須是 HTTP(S) 服務，並提供下列兩個可匿名存取的端點」
> 「MAA 會以固定間隔持續輪詢此端點（預設 1 秒，可在設定中調整）」

**方向是：MAA 主动轮询"我们的"端点。** 两个端点各司其职：

| 端点 | 方向 | 作用 |
| --- | --- | --- |
| 获取任务端点（`getTask`） | MAA → 我们 POST | MAA 带上 `user` / `device` 来领任务；我们回 `{"tasks":[...]}` |
| 汇报任务端点（`reportStatus`） | MAA → 我们 POST | 每执行完一项就回报 `task` / `status` / `payload`（截图任务时是 Base64 图片） |

**这条彻底改写了立项文档里的一句话。** `implementation.md:134` 与 `02-integration-research.md:333` 把这条链路描述为「服务器→手机→本机」，并注明「链路最长」。**事实是：不存在"服务器主动连本机"这一跳**——是 MAA 自己来取。**没有那一跳，就没有"链路最长"。**

### 1.2 用户已装的版本就支持（**本包最硬的一条实测**）

**【实测】** 本机 MAA 的版本与能力：

```
D:\mrfzmma\MAA.exe      ProductVersion = 6.18.0
D:\mrfzmma\MAA.dll      ProductVersion = v6.18.0+23feeddc...
```

**【实测】** `D:\mrfzmma\config\gui.new.json`（MAA 自己生成的**完整**配置模板）第 281–287 行存在这一组键：

```json
"RemoteControl": {
  "RemoteControlGetTaskEndpointUri": "",
  "RemoteControlReportStatusUri": "",
  "RemoteControlUserIdentity": "",
  "RemoteControlDeviceIdentity": "",
  "RemoteControlPollIntervalMs": 1000
}
```

`MAA.dll` 内也检索到 `RemoteControl` 与 `DeviceId` 字符串 **【实测】**。

**结论**：**能力已就位，用户只需在 GUI 里填两个 URL 与一个自定的用户标识。**

> **与既有调研的关系**：`02-integration-research.md:313` 判断「客户端侧只在 GUI 实现」。**该判断与实测一致**（配置项由 GUI 管理）。但该行同时把远程控制归入"三方方案"的语境，容易让人误以为要装东西——**实测是官方本体自带**。

### 1.3 能触发到多细？——**能"跑一次"，不能"跑哪一班"**

**【官方文档】** 任务类型里与基建相关的只有一个是：

```
"type": "LinkStart-Base"     // 立即根据当前设定，单独执行一键长草中的对应子功能
```

同一族还有 `LinkStart-Combat` / `-Recruiting` / `-Mall` / `-Mission` / `-AutoRoguelike` / `-Reclamation` 与 `LinkStart`（整体）。另有 `StopTask`、`HeartBeat`、`CaptureImage` / `CaptureImageNow`、`Toolbox-Gacha*`、`Settings-*`。

**注意 `LinkStart-Base` 的官方措辞**：是"根据**当前设定**"执行——**协议里没有任何字段能传班次、`plan_index` 或文件路径**。**【官方文档】** 与既有调研 `02-integration-research.md:313`（「只能下发 `LinkStart-Base`，带不了 `filename`/`plan_index`」）**一致**。

**含义（重要）**：

- ✅ 能表达：「**现在去跑一次基建换班**」——用的**是 MAA 客户端里当前那套配置**
- ❌ 不能表达：「**去跑第 2 班**」「**用这个文件**」「**把控制中枢换成这三个人**」
- ⚠️ 我们**已经知道用户的排班表是三班制**（12/6/6），而**协议给不了班次**。所以**"到点切到哪一班"这件事，协议层面就做不到**——它能做的只是"让 MAA 按它自己的规则跑一次"。

**若要按班次精确切换**，出路在 MAA 客户端自己的**换班时间条件**（`02-integration-research.md:298` 记过 `period` 字段 core 不处理）或 **maa-cli 的变体能力**（同文档 §6.3 表格），**不是**远程控制协议能给的。

### 1.4 触发后能拿到结果吗？——**能，这是它相对"自己点一下"的最大增量**

**【官方文档】** `reportStatus` 每完成一项任务就回报一次，字段含 `task`（对应任务 ID）、`status`（`SUCCESS` / `FAILED`）、`payload`。并且**同一任务 ID 不会被重复执行**（MAA 侧自己记录）。

**⚠️ 但有一个必须写清的陷阱**【官方文档原文】：

> 「**通常不論成敗皆彙報 SUCCESS**，僅特殊情形才會彙報 FAILED」

也就是说 **`status: SUCCESS` 并不等于"换班换成功了"**，它更多是"这条任务指令我处理完了"。**任何基于这个字段说"换班成功"的话术都是过度解读。**

另有一条能查实时状态的机制（**未实测**）：`HeartBeat` 任务会立刻返回，payload 是当前正在执行的任务 ID（无任务则为空串）。**【官方文档】**
→ **可用它做"现在在忙吗"的判断，而不是用它判断成败。**

### 1.5 还有一个"官方没提但不该忽略"的能力面

**【实测】** `gui.new.json` 同文件里还有两组与集成相关的键：

- **`RuntimeSettings.PreRunScript` / `PostRunScript`**（当前均为空）：MAA **跑前/跑后执行本机脚本**。这是**本机侧**的集成点，可用来"跑完通知服务器"。**好处**：不依赖轮询、不占端口；**代价**：逻辑落在用户机器上，要维护本机脚本。
- **`ExternalNotification.SendWhenComplete` / `SendWhenError`**（当前为 `true`）：MAA 跑完/出错**主动发通知**。**若这条通道能直接发到用户的 QQ，那么"结果反馈"这一半需求可能不需要我们写代码。** **【未验证】** 需确认它支持哪些通知渠道（本机 GUI 未展开核实，标【未拿到】）。

## 2. B · 网络路径（本包要回答的"环境问题"）

### 2.1 结论先行：**这条链路不需要任何穿透、隧道或端口放行**

因为 **MAA 主动出站**：

```
用户 Windows 机器                      服务器 bt-he1k（香港，公网可达）
  MAA ──(每 1 秒 POST /maa/getTask)──►  我们的插件（已有 Web API 能力）
  MAA ◄──(回 {"tasks":[...]})─────────
  MAA ──(POST /maa/reportStatus)─────►  插件 → 推送到用户 QQ
```

| 方案 | 可行性 | 安全面 | 维护成本 | 需用户装什么 |
| --- | --- | --- | --- | --- |
| **官方远程控制协议（本方案）** | ✅ **可行，已验证能力存在** | 中：端点**匿名可访问**，靠 `user`/`device` 自校验；**可用 HTTPS** | **低**：服务器侧写两个路由，用户填两个 URL | **什么都不用装** |
| 反向连接（本机常驻客户端主动连服务器） | ✅ 可行 | 好（不出站暴露） | **高**：要给用户写并维护一个客户端 | 一个小客户端 |
| 内网穿透（frp / cf tunnel / Tailscale / ZeroTier） | 可行但**不必要** | 视产品而定 | **高**：多一个常驻服务 + 多一套凭据 | 要装穿透工具 |
| 本机开公网端口 | 技术可行 | ❌ **最差**（家宽暴露一个可触发自动化的端口） | 中 | 要会配端口映射 |
| 纯人肉中转（只提醒，用户自己点） | ✅ 永远可行 | 最好 | **最低** | 无 |

**"内网穿透"这条要与本项目的既有经验对照**：工作区 `state/KNOWN-ISSUES.md` #16 记着 **Cloudflare Tunnel 在本环境极慢**（隧道连接绕道洛杉矶、边缘在达拉斯；同一页面直连 0.14s vs CF 1.42s），**服务器在香港**。**既然官方协议不需要穿透，就不该再引入穿透**——那等于主动把 #16 那个坑重新挖一遍。

**端口放行的现状**【实测，来自工作区清单】：服务器对外只开 `22 / 80 / 443`（8888 面板有 IP 白名单、888 被安全组拦）。**远程控制协议走 443 即可，不需要放行任何新端口**——这与立项文档 `02-integration-research.md:338` 写的「需端口放行或用隧道」**不同**：那条把"我们的端点要能被访问"理解成了"要新开端口"，**实测服务器 443 本来就通**。

### 2.2 HTTPS 是必须的（不是可选项）

**【官方文档原文】**：

> 「若該端點為 HTTP 協定，MAA 會在每次連線時發出不安全警告。**在外網上部署明文傳輸服務是極不推薦且危險的行為，僅供測試使用。**」

**【实测 · 本服务器现状】** 443 是 **HTTPS-by-IP + 自签证书**（工作区 `KNOWN-ISSUES.md` #17）。**后果**：MAA 侧很可能对自签证书报错或警告，**而 MAA 是 .NET 程序，它的 HTTP 客户端是否接受自签证书、能否配置跳过，我没有在 MAA 侧验证过**——**【未拿到】**，这是本报告**最需要下一步实测的一个点**。

**若自签证书不通**，三条退路（按推荐序）：① 给服务器一个**真证书**（需域名，而工作区 ADR-0004 记着**未备案域名走 80/443 会被网络层拦**【实测】）；② **让端点只走本地/隧道**（但那就是本机 → 服务器，又回到"MAA 要能访问端点"的老问题）；③ **接受明文 HTTP**（官方明确说"仅测试"，**而这条链路承载的是"能让你电脑跑自动化"的指令，我不建议**）。

> **这一条是本方案真正的技术风险**，而且它**不在"能不能做"上**，在"**证书这一关过不过得去**"上。

### 2.3 电脑没开机怎么办（用户已明确要求"优雅失败"）

**【实测】** MAA 只在运行且开了远程控制时轮询。**电脑关机 = 没人来取任务**。

**因此服务器侧必须自己管生命周期**，否则会犯本项目最忌讳的"看起来成功但什么都没发生"：

1. **任务要有 TTL**：写进队列后 N 分钟无人领取即作废，并**明确告诉用户"你的电脑当时没开，这条没有执行"**——不能静默。
2. **不要无限堆积**：同一类任务（如"跑一次基建"）在队列里**只保留最新一条**，否则开机瞬间会连跑 N 次。
3. **用 `HeartBeat` 判断在不在**（可选）：要"发指令前先问一句在不在"，靠它而不是靠猜。

## 3. C · 需求侧的未知（**必须先问用户**）

### 3.1 为什么这一节是本报告的核心

**【实测】** 用户现在的 MAA 已经在跑定时任务，而且用的是**他自己从 riic.autos 导出的三班排班表**：

```json
"Infrast.DefaultInfrast": "user_defined",
"Timer.Timer1": "True",  "Timer.Timer1Hour": 4,  "Timer.Timer1Min": 0,
"Timer.Timer5": "True",  "Timer.Timer5Hour": 23, "Timer.Timer5Min": 0
```

**【实测·既有文档印证】** `02-integration-research.md:15` 与 `:305` 记着同一件事：**排班文件 `arknights-infra-schedule-maa.json` 来自 riic.autos，MAA 里已配了 04:00 / 23:00 两个定时自动启动**。

**这意味着「到点自动跑 MAA」在他机器上早就成立了。** 立项文档自己也把这件事列成了 **R1 最高风险："需求前提未澄清（MAA 已能自动换班）→ 可能重复建设"**（`02-integration-research.md:430`），并留了 **P1–P4** 四个待答问题（`:465-468`）。**这四个问题至今没有答案。**

**所以本方案的价值不在"定时"**——定时 MAA 自己就能做，而且已经有 8 个定时槽位（`Timer1`–`Timer8`，当前用了 2 个）。**要论证做它，必须找到一个定时器给不了的东西。**

### 3.2 定时器给不了、而远程触发能给的（**候选**，需要用户确认他要哪个）

| 候选增量 | 定时器能否做到 | 说明 |
| --- | --- | --- |
| **结果回到 QQ** | ❌ 做不到 | 定时器跑完只在电脑上弹通知/写日志；**远程协议能让我们把结果（含截图）推到 QQ** |
| **临时按需触发一次** | ❌ 做不到 | 「今天想补跑一次」→ 现在得去开电脑点 GUI；远程可 `StopTask` / 随时下发 |
| **在 QQ 里改时刻并即时生效** | ⚠️ 勉强能做到 8 个槽位，但要开 GUI 改 | **注意**：三班制只需 3 个时刻，**8 个槽位够用**——**这一条不构成理由** |
| **电脑没开时告知用户"没跑成"** | ❌ 做不到（它没开，什么都不知道） | 需要服务器侧判断，见 §2.3 |
| **按班次精确切换** | ✅ MAA 侧的换班时间条件/多定时器可做 | **远程协议做不到**（§1.3），**这一条不能拿来做卖点** |

**⇒ 真正站得住的增量只有两条：把结果推回 QQ、以及按需远程触发一次。**
**若有人的答案是"我只想要结果通知"，那这件事的形态不是"远程触发"，而是"接 MAA 的完成通知"——那**可能更省事**（见 §1.5 的 `ExternalNotification` 与 `PostRunScript`）。

### 3.3 需要用户回答的问题清单（**具体、可回答**）

**A. 先回答那个决定"做不做"的（就是立项留下的 P1–P4，重新问一次，问得更具体）**

1. **你现在的 04:00 / 23:00 两个定时器，实际跑的结果你满意吗？** 具体是：**换班换对了吗**（还是经常"没换到该换的那一班"）？
   - 若答案是「经常没换对」→ **真正的问题是"MAA 切不到正确的班次"**，那要解决的是**换班时间条件或 plan 选择**，**不是"谁来触发"**。**这会把本方案整个否掉。**
2. **你会在电脑没开的时候期待它跑吗？** 如果会，那**任何依赖本机的方案都只能"告知你没跑成"**，不能"让它跑成"。
3. **你现在是怎么知道它跑没跑的？** 是看电脑、还是根本不知道？
   - 若答案是「根本不知道」→ **"结果推回 QQ"就是真正的缺口**，本方案值得做。
4. **你想要"到点自动跑"还是"机器人问一句、你确认再跑"？**
   - 前者 MAA 定时器已经能做；**"你确认再跑"才是本方案独有的**（因为它需要服务器侧存任务 + 等确认）。

**B. 环境问题（决定能不能落地）**

5. **那台电脑平时开机吗？** 一天大约几小时、什么时段？（决定任务 TTL 与"优雅失败"话术怎么设计）
6. **MAA 平时是开着 GUI 吗**？还是跑完就关？（决定"轮询是否常在"）
7. **你能不能接受在 MAA 设置里填两个 URL 和一个自定标识？**（这是整个方案对用户的**全部**要求，**不需要装任何新东西**）

**C. 取舍问题（决定形态与我们的工作量）**

8. **如果结果通知就够**（你的电脑跑没跑成、跑完什么样），**那我们不必做"远程触发"**——只需要让 MAA 把完成通知发出来。**你要哪一个：仅仅是通知，还是也要能远程下指令？**
9. **服务器到 MAA 的通道必须 HTTPS**（官方明确说 HTTP 仅供测试）。我们服务器目前是**自签证书**（浏览器会提示不安全）。**你更在意"省事"（那就得先给服务器配一个真证书 / 或者接受明文）还是"安全"？**
10. **能不能接受"这台机器被服务器上的指令触发自动化"这件事本身？** 需要写清：**端点是匿名可访问的**，我们会用 `user` + `device` 做校验，但**任何拿到那串标识的人都能让这台电脑跑基建**。

## 4. D · 与现有设计的关系（可复用件，避免重复造）

**【实测·项目内部】** 本项目已经有的、本方案可以直接复用的：

| 已有件 | 复用方式 | 出处 |
| --- | --- | --- |
| **插件 Web API 能力** | `/maa/getTask`、`/maa/reportStatus` 就是两个路由，`context.register_web_api()` 已跑通（页面与配置 API 在用） | `modules/shift_reminder/webapi.py`、`main.py` |
| **换班时刻模型** | "什么时候该换班"已经算好（三班 + 提前量 + cron） | `modules/shift_reminder/schedule.py`、`scheduler.py` |
| **推送到 QQ 的通道** | 结果通知直接复用 `_push` 那条路（含失败熔断与发送记录） | `modules/shift_reminder/notify.py` |
| **"等你确认"的交互** | AstrBot 自带 `@session_waiter` + `SessionController`（立项调研已记） | `02-integration-research.md:225` |
| **模块自动发现 + 契约** | `maa` 作为第三个模块接入，宿主不认识它 | `modules/`、`core/registry.py` |
| **告警思路**（运维侧） | "用还活着的通道报告出问题的那一侧" | `scripts/healthcheck/check-napcat-login.sh` |

**这条链路里谁能控制、谁依赖用户**：

| 环节 | 谁负责 | 可控性 |
| --- | --- | --- |
| 什么时候该换班 | **我们**（已有逻辑） | ✅ 完全可控 |
| 要不要去触发 | **用户**（回一句话）或规则 | ⚠️ 依赖用户配合（若要确认式） |
| 指令能否送达 | **MAA 主动来取** | ⚠️ 依赖**电脑开着且 MAA 在跑** |
| 实际换班动作 | **MAA**（它自己那套配置） | ❌ **我们只能"让它跑"，管不了它跑哪一班** |
| 结果回传 | MAA → 我们 → 用户 | ⚠️ `SUCCESS` 不代表换班成功（§1.4） |

## 5. 结论与建议

### 5.1 技术结论（都有实测或官方文档支撑）

1. **能做，而且比立项时想的简单**：官方协议 + 已装 6.18.0 支持 + **无需穿透/端口** + **用户零安装**。
2. **边界是硬的**：**只能触发"跑一次当前配置的基建"，不能指定班次。** 若要精确切班次，得走 MAA 侧的换班时间条件或 `maa-cli`，**不是本协议**。
3. **`status: SUCCESS` 不能当"换班成功"**——官方原文说通常不论成败都报 SUCCESS。
4. **最大技术未知是证书**：端点必须 HTTPS，而服务器现在是**自签证书**；MAA（.NET）能否接受/配置跳过，**【未验证】**。**这一条不解决，方案落不了地。**
5. **电脑没开机时必须优雅失败**，且要主动告知"没跑成"——否则就是我们最忌讳的那种静默。

### 5.2 需求结论（**这才是本报告的重点**）

**用户机器上"MAA 到点自动换班"早就成立了**（两个定时器 + riic 导出的三班表）。立项文档把这条列为 **R1 最高风险**，留了 **P1–P4** 四个问题，**至今未答**。

**所以我的建议是：先不要动手实现，先把 §3.3 的 A 组四个问题问掉。** 其中**第 1 条是决定性的**：

- 若用户答「**定时器经常换不到正确的那一班**」→ **真问题是"班次切换"，本方案（远程触发）解决不了它**，该往 **MAA 换班时间条件 / `maa-cli` 的 `plan_index`** 方向查。**本方案应当暂缓或放弃。**
- 若用户答「**我只是不知道它跑没跑、跑成什么样**」→ **真缺口是"结果反馈"**，那么**最小实现不是远程触发，而是接 MAA 的完成通知**（§1.5 的 `ExternalNotification` / `PostRunScript`），工作量小一个数量级。
- 只有当用户明确要「**临时想让它跑一次**」或「**要机器人问一句、我确认再跑**」时，**远程控制协议才是那个对的工具**。

### 5.3 如果要做，推荐形态

**(a) 先做一个"最小可验证"版本**，只为回答"证书这一关过不过得去"：

1. 服务器加**两个只回固定内容的端点**（`getTask` 返回空 tasks、`reportStatus` 记一行日志）；
2. 让用户在 MAA 设置里填上这两个 URL 与一个标识；
3. **观察 MAA 是否连得上**（这一步会同时验证：网络通不通、自签证书过不过、MAA 的轮询行为如何）。
   **这一步不涉及任何换班逻辑**，风险最低，却能一次性消掉最大的未知。

**(b) 通过了再做功能**，且**必须**带上：

- 任务 **TTL + 去重**（电脑没开时不堆积、不静默）；
- **结果如实转述**（`SUCCESS` 就说"指令已执行"，**不说"换班成功"**）；
- 用**已有的 `_push` 通道**送结果（含失败熔断）；
- **不承诺班次精度**（文案里不许暗示"帮你切到第 2 班"）。

### 5.4 若结论是"不做"

**完全站得住**，理由有两条：

1. **用户已经能用 MAA 定时器完成"到点跑"**，而本方案唯一的独有增量是"按需触发 + 结果回 QQ"；若用户对这两条无感，**这层就是重复建设**。
2. **它引入了一条"能让家里电脑跑自动化"的匿名被触发通道**，安全面比"只提醒"大得多，**而收益尚未被证实。**

### 5.5 未验证 / 未拿到（如实列出）

| # | 项 | 状态 |
| --- | --- | --- |
| 1 | **MAA（.NET）对自签 HTTPS 证书的行为**（接受？报错？可配置跳过？） | **【未验证】本方案第一风险** |
| 2 | `ExternalNotification` 支持哪些通知渠道（能否直接发到 QQ） | **【未拿到】** |
| 3 | `HeartBeat` 任务的实际返回（能否可靠判断"正在忙"） | **【未验证】**（仅官方文档） |
| 4 | MAA 远程控制的**鉴权强度**：端点匿名，`user`/`device` 被猜中会怎样 | **【未拿到】**（官方未规定，取决于我们自己的实现） |
| 5 | 用户 MAA 侧的**完整设置界面**（远程控制填在哪一页） | **【未实测】**（只从配置模板确认键存在，未打开 GUI 核对路径） |
| 6 | **用户的真实需求**（§3.3 的 A 组） | **【未答】整个方案的前提** |
