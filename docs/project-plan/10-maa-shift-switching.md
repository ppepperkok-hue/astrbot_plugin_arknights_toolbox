# MAA 到底靠什么决定「现在用哪一班」

> **本包要回答的问题**：所有者已决定关掉 MAA 的定时自动跑、改用插件的「提醒 + 触发」。
> 但远程控制协议只能下发 `LinkStart-Base`（「按当前设定跑一次」），**没有任何字段能指定班次**。
> 那么「用哪一班」到底是谁决定的？**若答错，可能做出一个「能跑、但永远跑同一班」的东西。**
>
> **红线遵守**：MAA 是 **AGPL-3.0**，本项目是 MIT。本文**未复制任何 MAA 代码或资源文件**；
> 引用仅为**极短的字段名、配置值、界面文案**（事实性标识符，用于说明行为），
> 且全部来自**只读**观察。所有 MAA 侧操作均为读文件 / 读二进制字符串，**未运行 MAA、未修改任何配置**。
>
> **证据强度标注**：**【实测】**＝本机只读观察；**【官方文档】**＝MAA 官方文档站原文；
> **【配置实证】**＝从本机配置文件的实际内容/差异推出；**【未验证】**＝推断，未证实。

## 0. 一句话结论

**班次由 MAA 自己轮换，靠的不是任何外部调度，而是「每次换班完成后，把计划索引前进一个」；
这个索引写在配置文件里（`PlanSelect`），因此会持久化。**

**⇒ 关掉定时器之后，班次仍然会轮换——只要有人触发一次基建任务。而「触发」正是我们能做的事。**

**⇒ 远程触发在「班次正确性」上不输给定时器**，而且能做得更准（对齐用户真实的换班时刻，而不是 MAA 的固定时刻）。

**⇒ 但有一把双刃剑：触发次数 = 换班次数。多触发一次，班次就多前进一班。去重是硬要求，不是优化项。**

## 1. 机制：三层，各管一段

排查的关键在于**这三层是分开的**，而先前把它们混为一谈：

```
第一层（文件）  排班文件 plans[] 里的 period 时间段
                    ↓  GUI 读取并计算
第二层（GUI）    plan 索引（配置字段 PlanSelect）
                    ↓  作为参数传给核心
第三层（核心）   MaaCore 的 asst::InfrastTask::parse_and_set_custom_config
                读 plan_index，直接索引 plans[]
```

### 1.1 第一层：`period`——**可选**，而且用户没有

**【官方文档】** [基建排班协议](https://docs.maa.plus/zh-cn/protocol/base-scheduling-schema.html) 对 `period` 的注释原文：

> ```json
> "period": [
>     // 换班时间段，可选
>     // 若当前时间在该区间内，则自动选择该计划（整个 json 文件中可能包含多个计划）
>     // 如果该字段不存在，则每次换班结束后，自动切换为下一个计划
>     // core 不处理该字段，若您使用接口集成 maa，请自行实现该逻辑
> ],
> "duration": 360, // 工作持续时长（分钟），保留字段，目前无作用
> ```

**这两行注释就是整个答案**：

| `period` | 行为 |
| --- | --- |
| **存在** | 按当前时间落在哪个区间来选计划 |
| **不存在** | **每次换班结束后，自动切换为下一个计划** ← **用户走的是这条** |

**⚠️ 一处必须纠正的旧口径**：本项目 `09-maa-trigger-assessment.md` 与更早的调研都记过
「`period` 字段 core 不处理」——**那句话本身没错，但它容易被误读成「period 没用」。**
**core 不处理，是因为 GUI 处理**：GUI 读 `period` 算出索引，再把索引交给 core。
**「core 不处理某字段」≠「该字段无效」。**

### 1.2 第二层：`PlanSelect`——GUI 维护的**计划索引**（会自动前进）

**【实测】** 本机生效配置 `D:\mrfzmma\config\gui.new.json` 的基建任务块：

```json
{
  "$type": "InfrastTask",
  "Mode": "Custom",
  "CustomFileType": "user_defined",
  "Filename": "D:\\Users\\Administrator\\Downloads\\arknights-infra-schedule-maa (2).json",
  "PlanSelect": 1
}
```

### 1.3 第三层：`plan_index`——核心只认一个数字

**【实测】** `MaaCore.dll` 内的字符串，把核心行为说得很死：

```
filename is not set while custom mode is enabled
plan_index
asst::InfrastTask::parse_and_set_custom_config
custom infrast file does not exist:
failed to open json file:
| custom json: ... plans ... , index: ...
index is out of range, plans size: ..
rooms ... skip ... autofill ... sort ... use_operator_groups
```

**⇒ 核心读 `plan_index`（数字），直接索引 `plans[]`**；越界时报
`index is out of range, plans size: N`。
**⇒ `plan_index` 不是远程控制协议能给的字段**（协议的任务体里没有它）。
**⇒ `planTimes` 在 `MaaCore.dll` 与 `MAA.dll` 里各出现 0 次**——**两边都不读它。**

> **关于 `planTimes`**：它是排班文件顶层的一个字段（用户文件里是字符串 `"3班"`；
> `scheduleType` 内部另有一个同名数字字段 `planTimes: 3`，那是**布局统计**：
> `{"planTimes":3,"trading":2,"manufacture":4,"power":3,"dormitory":4}`）。
> **它是给人看的元数据，不参与核心或 GUI 的班次判定。**

## 3. 最硬的一条实测：索引确实在前进，而且被写回配置

**【配置实证】** 本机配置与其自动备份的**全量差异**只有两处：

```
$.Configurations.Default.TaskQueue[2].PlanSelect
    live   = 1
    backup = 0

$.Configurations.Default.TaskQueue[4].VisitFriendsLastTime
    live   = '2026/09/29 00:00:00'
    backup = '2026/09/28 00:00:00'
```

（时间戳：`gui.new.json.bak` = 12:53:35，`gui.new.json` = 13:13:24。）

**这条差异链证明了三件事**：

1. **`PlanSelect` 会自动前进**（0 → 1）；用户并未手动改过它——他自己只是跑了一次任务。
2. **它被写回配置文件**（否则不会出现在文件里）⇒ **轮换状态持久化**，
   意味着 **MAA 重启后能接着算**，不依赖进程常驻。
3. 同一次写入里 `VisitFriendsLastTime` 从 28 日变成 29 日，说明**确实跑过一次完整任务队列**
   （信用购物每天一次），**索引前进与"跑了一次"时间上吻合**。

**⇒「每次换班完成 → 计划前进一个 → 写回配置」这条链路，两端的证据都齐了**
（官方文档给了规则，配置差异给了行为）。

## 4. 这对「关掉定时器、改用我们的触发」意味着什么

### 4.1 好消息：**不会丢轮换**

因为前进的触发点是「**一次基建任务的完成**」，而不是「定时器的整点」。
**定时器只是"到点启动任务"的一种触发器**——它是**触发器**，不是**班次机制**。

**【实测】** 佐证：本机定时器段

```json
"Timers": { "CustomConfig": false, "List": [
  { "Id": 0, "IsEnabled": true, "Config": "Default", "Hour": 8,  "Minute": 0 },
  { "Id": 1, "IsEnabled": true, "Config": "Default", "Hour": 20, "Minute": 0 },
  { "Id": 3, "IsEnabled": true, "Config": "Default", "Hour": 2,  "Minute": 0 }
]}
```

三个定时器**都指向同一个配置档 `Default`**，而**每个定时器自带的 `Config` 字段说明定时器确实能选配置档**；
`CustomConfig: false` 表示**没有启用"每个定时器各用一套配置"**。
⇒ **用户的定时器没有在做"切配置"这件事**；**它只是到点跑一次**。

### 4.2 ⇒ 我们的触发与定时器**在班次上是等价的**，而且可能更准

| 维度 | MAA 定时器 | 我们的触发 |
| --- | --- | --- |
| 启动一次基建任务 | ✅ | ✅ |
| 完成后计划自动前进 | ✅ | ✅（同一机制） |
| 时刻能不能对齐真实换班时间 | ⚠️ 只能设整点（8 个槽位） | ✅ 用我们已有的三班模型 |
| 电脑没开时 | 静默跳过，用户不知道 | 可**明确告知"没跑成"** |
| 结果回 QQ | ❌（只在电脑上弹窗） | ✅ 复用既有推送通道 |

### 4.3 坏消息（必须写进设计）：**触发次数 = 换班次数**

计划索引**每跑一次前进一个**。所以：

- **误触发一次 ⇒ 班次多前进一班**，而且**会持久化**（写到配置里），
  **不会自己纠正**；
- **同一次换班触发两次 ⇒ 跳过一班**，用户的排班就乱了。

**⇒ 去重不是"优化项"，是正确性要求。** 09 号文档 §5.3(b) 已列了「任务 TTL + 去重」，
**本包把它的优先级从"应做"提升为"必须做对"**，并补一条：

- **同一换班时刻只允许产生一个任务 ID**；重试要复用同一个 ID，
  **绝不能让"重试"变成"多跑一次"**（MAA 侧对同一任务 ID 有去重，`reportStatus` 文档说明确
  「同一任务 ID 不会被重复执行【官方文档】」——**这正好可以被我们利用：重试复用 ID，而不是新发一个**）。

### 4.4 另一条推论：**没人触发就没有换班**

关掉定时器之后，**如果没有任何东西触发，排班就停在当前这一班**（当前 `PlanSelect: 1`，
即 `plans[]` 里的第 2 套 —— 索引 0 基，见 §1.3 的越界报错格式）。
**这是"关掉定时器"的直接代价，必须让用户知情**：
我们的提醒若不落到"触发"，换班就会**停在原地**。

## 6. 给决策的一句话

**「关掉定时器 ⇒ 丢轮换」这个担心不成立**：轮换是 MAA 内置的，靠"跑一次就前进一班"，
且状态持久化。**所以我们的触发是定时器的合格替代品，并且在"告诉用户跑没跑成"这件事上明确更强。**

**但代价与纪律必须一起说清**：

1. **没人触发 ⇒ 停在当前班**（所以提醒必须能落到触发）；
2. **触发次数必须严格等于换班次数**（多一次就跳一班，且不可自动纠正）；
3. **重试要复用任务 ID**，不能新发一个；
4. **话术不许承诺"帮你切到第 N 班"**——我们只能"让它跑一次"，**跑完前进到哪一班是 MAA 按它的规则决定的**。

**在需求侧仍有一件事值得所有者确认**（比本包的技术结论更影响取舍）：
**他是否接受「关掉定时器后，换班不再自动发生，而取决于我们有没有触发」**。
若他其实希望"即使没人管也能自动换"，那**定时器不该关**——
本包的技术结论**不改变**这一点，它只澄清了"关掉定时器到底会失去什么"。

## 7. 落地：确认制派任务（2026-09-29 实测）

本包结论落地成了 `modules/maa/` 的「**确认制派任务**」。这里记实测与设计依据。

### 7.1 协议原文（**实抓 zh-cn 页面**，逐条对照）

来源：[远程控制协议](https://docs.maa.plus/zh-cn/protocol/remote-control-schema.html)（HTTP 200 实抓）。四句直接决定设计的话：

| 原文 | 对我们的含义 |
| --- | --- |
| 任务体形如 `{"id": "<唯一 id>", "type": "<任务类型>"}` | 只有两个键。**多塞字段没有收益**，却会让人以为它能带参数（例如班次——它带不了） |
| **「该端点应当可以重入并且重复返回需要执行的任务」** | 下发了**不必**只给一次；重复返回是**对的** |
| **「MAA 会自动记录任务 id，对于相同的 id，不会重复执行」** | ⇒ **只要「同一次换班 ⇒ 同一个 id」成立，重复轮询与重试就不可能变成「多跑一次」** |
| `LinkStart` = 启动一键长草；`LinkStart-Base` = 「立即根据当前配置，**单独执行**一键长草中的对应子功能」 | 所有者要的「跑完全套流程」= `LinkStart`（默认）；`LinkStart-Base` 只跑基建 |

### 7.2 自签证书：**第一风险已实测确认**（§5 未验证表第 6 条）

MAA 报的是：

```
连接测试失败，原因：The remote certificate is invalid because of
errors in the certificate chain: UntrustedRoot.
```

⇒ **MAA 拒绝自签证书**。这不是网络/地址/Key 的问题。把服务器那张证书（单张自签，`subject == issuer`）导入 Windows 的**「受信任的根证书颁发机构」**并重启 MAA 之后，连接测试通过；随后服务器日志出现 `✅ 首次收到 MAA 请求`，nginx 访问日志可见 `MaaWpfGui/v6.18.0` **每秒一次**、`200 12`（12 字节＝`{"tasks":[]}`）。

**这条写进了用户指南**（`docs/guides/maa-remote-control.md` 第 6 节），因为**任何用自签证书的用户都会撞上它**。

### 7.3 去重的两条不变量（`modules/maa/queue.py`）

§4.3 说去重是正确性要求；落地上把它拆成两条**可测**的性质：

1. **同一次换班 ⇒ 同一个任务 id**。`task_id_for(slot_key)` 是 `uuid5` 纯函数，**跨进程重启稳定**。
   配合「同 id 不会重复执行」，**重复确认、重复轮询、重试都不会变成多跑一次**。
   这条是**结构性安全**——它不依赖我们在内存里记得住什么。
2. **同一时刻最多一个未结任务**。挡的是另一类错：上一个还没回报，用户又确认一次，
   MAA 会跑完第一趟接着跑第二趟——**那时两个 id 不同，MAA 侧的去重救不了我们**。

过期也分两种窗口（成因不同，处置相反）：

| 情况 | 处置 | 为什么不这样会错 |
| --- | --- | --- |
| 派出去**从来没人取**（电脑没开） | 超过 `task_ttl_minutes`（默认 30）作废，**明确告知**；**不记「已做过」** | 记了就再也补不了；而「静默留着、三小时后突然跑掉」会让班次在与换班无关的时刻前进 |
| 取走了**却一直没回报** | 超过 `fetched_ttl_minutes`（默认 240）作废并**记「已做过」** | 它多半已经跑了，**不能再给第二次机会** |

### 7.4 仍未打通的一条：「到点询问」需要一条**单一事实来源**的通道

任务书要求到换班时刻主动询问用户。**这一条没有实现，卡在架构上**，四堵墙都已核实：

1. 宿主只按 `config_key` 注入**自己那一段**（`core/registry.py` 的 `start_all`、`main.py` 的
   `_apply_config_to_modules`），C3 裁决原文：模块「**不知道别的模块段存在**」；
2. `shift_reminder` **不持久化**班次表（`state.json` 里只有 `bound_umo` / `imported_roster` / 幂等键）；
3. 契约（`extension.md` §2 结尾）写着模块「**不许 import 别的模块**」；
4. §4 的既有规定是「共享逻辑抽到 `core/`，**别复制**」。

**⇒ 复制时刻或偷读别人的配置段都会让「班次时刻」变成两份，而漂移的代价正是本文全篇在防的那件事。**
所以 `maa` **没有绕**：派任务先由 `/ak maa run` 手动触发。班次模型已开始往 `core/shifts.py` 收拢
（那是第 4 条的合规解法），**剩下的只差把「值」送到 `maa` 这一步**——需要一次动地基的裁决。

**这一段的意义**：`09` 号文档把「需求前提未澄清」列为最高风险；本节把「技术上还差什么」也说清了——
**现在挡在路上的既不是工时、也不是 MAA 的能力，而是一条该由谁负责的通道。**
